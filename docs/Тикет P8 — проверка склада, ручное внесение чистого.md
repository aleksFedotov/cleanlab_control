# Тикет P8 — проверка склада: цифры до подтверждения, валидация «есть чистое», ручное внесение чистого

## Контекст

На экране работника и в карточке стирки есть действие «Проверить на складе»
(`confirmStorageCheck`, server/wash.js) с тремя исходами: `has_dirty` (есть
грязное), `no_dirty` (нет белья), `already_clean` (есть чистое бельё).

Проблема в ветке `already_clean`: она только ставит стирке
`status='ready_clean'` + `done_at` и пишет в Log. Факт наличия чистого белья
на складе **не проверяется**, clean-запись в Storage **не создаётся**. Если
работник или владелец подтверждает «есть чистое», когда у клиента нет ни одной
открытой clean-записи, система расходится сама с собой:

- карточка уходит в «Готово», отчёт дня считает стирку завершённой (0 кг),
смену она не блокирует;
- но `notReadyForDelivery_` считает честно: `ready_clean` не входит в
done/stored, склад пуст → вечером владельцу улетает Telegram «не готовы к
развозу: нет чистого белья». Карточка зелёная, телеграм красный;
- завтра водителю по этому клиенту брать нечего — открытых clean-записей нет.

Вторая половина контекста: сценарий «бельё физически лежит на полке, но записи
в системе нет» (досистемный запас, бельё с бумажных накладных, потерянная
запись) сейчас не имеет легального пути вообще — clean-записи создаёт только
`completeWash`. Ручного внесения чистого нет ни у работника, ни у владельца.

Автосоздавать clean-запись из `already_clean` **нельзя**: clean-запись несёт
вес, штуки и мешки, по которым водитель сверяет выдачу. Пустая запись =
фантомная готовность: `storageSummary` покажет `clean > 0`, предупреждение
погаснет, а вывозить будет нечего.

Плюс отдельная неудобство-дыра: работник выбирает вердикт вслепую — модалка
показывает только имя клиента и три кнопки, хотя сводка склада с цифрами
уже считается сервером при сборке карточек. Расхождение с полкой/накладной
должно быть видно до подтверждения, а не после.

Решение — связка из пяти частей: валидация, UI-гард, ручное внесение
(работник + владелец), колонка мешков у Storage, цифры склада в модалке.

Зависимости: master после R3/R4 (server/wash.js, `db.transaction_`,
`Storage.visit_id`). Нумерация схемы продолжается: текущая 9 → станет 10.

---

## Часть 1. Серверная валидация `already_clean` (server/wash.js)

В `confirmStorageCheck`, ветка `already_clean`, до смены статуса:

```js
if (verdict === 'already_clean' &&
    openStorage_(w.client_id, 'clean', laundryId).length === 0) {
  return err_('Чистого белья этого клиента на складе нет. ' +
    'Если бельё физически на полке — внесите его вручную.');
}
```

- Проверка внутри существующей транзакции команды, до `updateRow_` и до
`logEvent` (отказ не должен оставлять следов).
- `openStorage_` уже отсекает `consumed_at='driver'` — чистое, которое у
водителя, «на складе» не считается. Это правильно, оставить как есть.
- Ветки `no_dirty` и `has_dirty` не трогаем: `has_dirty` осознанно создаёт
dirty-запись (она не несёт веса/штук, безопасно), `no_dirty` безвреден
(повторная проверка всегда доступна).

## Часть 2. UI-гард в StorageCheckModal (client/src/app/worker/StorageCheckModal.tsx)

У карточки уже есть `w.has_clean` (его считает `decorate` в getDayList из
`storageSummaryByClient_`).

- При `!w.has_clean` кнопка «Есть чистое бельё» — `disabled`, с подсказкой
рядом: «По учёту чистого на складе нет».
- Под ней — кнопка «Внести чистое вручную…» (открывает форму части 3).
- Гард — только подсказка: основной страж остаётся серверная валидация
(карточка может быть устаревшей). Ошибку сервера показывать как сейчас.

## Часть 3. Ручное внесение чистого (работник + владелец)

### API

Новый метод: `addManualClean(session, clientId, weightKg, itemsTotal, bags, comment)`.

- `server/api.js`: `addManualClean: WORKER_OWNER` в API_ROLES, разводка на
`wash.addManualClean`.
- Команда в `server/wash.js` (рядом с `confirmStorageCheck`), тело —
`db.transaction_`.

### Валидации (все — до любой записи)

1. Клиент существует в этой прачке и `active === 'да'`.
2. `bags` обязательны: целое > 0. Мешки — единственная физическая сверка
водителя, без них запись бессмысленна.
3. Вес обязателен (> 0), кроме клиентов с `accounting === 'count'`. У
count-клиентов обязателен `itemsTotal` (> 0). При `both` — вес обязателен,
штуки опциональны.
4. `comment` обязателен: непустой после trim. Это исключительный путь, «откуда
бельё» должно быть записано.

### Эффекты

- `addStorageEntry_(clientId, 'clean', { weight_kg, items_total, bags }, laundryId)`
— с `bags` (часть 4). `wash_id` пустой — стирки за записью нет, и это
принципиально (см. «Что не входит»).
- `logEvent(actorOf_(session), 'storage_manual_clean', entry.id,
{ client_id, kg, items, bags, comment }, laundryId)`.
- Telegram владельцу при действии работника — существующий
`notifyOwnerOnWorkerAction_` (он сам отсекает владельца), отправка после
коммита: «📦 {актор}: чистое внесено вручную — {клиент}: {кг} кг, {n} мешк.
({comment})».

### UI работника

Новая модалка `ManualCleanModal` (client/src/app/worker/): открывается из
StorageCheckModal (часть 2). Поля: вес (скрыт/необязателен при
`w.client_accounting === 'count'` — режим уже есть на карточке), количество
штук (при `count`/`both`), мешки, комментарий. После успеха: инвалидация
`operational` (обновится `has_clean`), toast «Чистое внесено ✓ — подтвердите
проверку склада», возврат в StorageCheckModal, где «Есть чистое бельё» уже
доступно. Два явных шага намеренно: внесение и подтверждение — разные факты.

### UI владельца

Страница «Склад» (client/src/app/(dashboard)/storage/page.tsx): кнопка
«＋ Внести чистое» в секции чистого. Форма: выбор клиента (активные прачки),
те же поля. Права — серверные (WORKER_OWNER), UI просто показывает действие.

## Часть 4. Колонка `bags` у Storage (схема v10)

Сейчас мешки живут на стирке (`Washes.bags`), а складская сводка и экран
водителя читают их через `wash_id` записи. У ручной записи стирки нет — без
колонки мешки везде покажутся нулём, и сверка водителя сломается ровно там,
где нужнее всего.

- `server/schema.js`: `HEADERS.Storage` += `'bags'` (после `'items_total'`);
`SCHEMA_VERSION` 9 → 10. DDL не нужен: `createTables_` сам донесёт колонку
авто-ALTER'ом. Миграция не нужна: у старых строк `bags=''` — чтение
через fallback (ниже).
- `addStorageEntry_`: `bags: opts.bags || ''` (server/storage.js).
- Чтение — единое правило «свои мешки, иначе мешки стирки». Сделать helper в
server/storage.js:

```js
// Мешки записи: явные (ручное внесение, P8) или через стирку (как раньше).
function storageBagsOf_(s, washBags) {
  if (s.bags !== '' && s.bags !== undefined) return Number(s.bags) || 0;
  return washBags[s.wash_id] || 0;
}
```

- `storageSummaryByClient_`: `cleanBags` через `storageBagsOf_`.
- Агент находит все места, где мешки чистого читаются через стирку (grep по
`cleanBags`, `washBags`, чтение `bags` у стирок складских записей на экране
водителя и склада), и переводит их на helper. Поведение для записей из
стирок не меняется.

## Часть 5. Цифры склада до подтверждения (StorageCheckModal)

`storageSummaryByClient_` уже считает по каждому клиенту всё нужное (число
грязных/чистых записей, кг, штуки, мешки чистого), но в карточку стирки
попадают только флаги `has_dirty`/`has_clean`. Пробрасываем цифры.

**Сервер** (server/api/washes.js, `decorate` в getDayList — ноль новых
запросов, сводка уже в руках):

```js
const s = storage[w.client_id] ||
  { dirty: 0, clean: 0, cleanKg: 0, cleanItems: 0, cleanBags: 0 };
w.has_dirty = s.dirty > 0;
w.has_clean = s.clean > 0;
w.storage = { dirty: s.dirty, clean: s.clean,
  clean_kg: s.cleanKg, clean_items: s.cleanItems, clean_bags: s.cleanBags };
```

Бонус: те же цифры появляются у карточек «Осталось со вчера» — `decorate`
общий (P7). Мешки считаются через `storageBagsOf_` (часть 4), поэтому ручные
записи учитываются корректно.

**Типы**: `DayWash.storage` в client/src/types/api.ts.

**UI**: блок «Сейчас по учёту» в StorageCheckModal над кнопками вердиктов:

- чистое: «12 кг · 40 шт · 3 меш.» или «нет»;
- грязное: «N партий» — веса у грязного нет by design (появляется при
  взвешивании на старте стирки), поэтому только число записей.

Модалок две — у работника (client/src/app/worker/StorageCheckModal.tsx) и у
владельца в карточке стирки ((dashboard)/wash/[id]/StorageCheckModal.tsx):
правим обе или выносим общий блок.

## Тесты (server/test/wash.test.js; при необходимости — отдельный файл)

1. `already_clean` без открытого clean у клиента → ошибка; статус стирки не
изменился; в Log не добавилось `storage_check`.
2. `already_clean`, когда чистое клиента уже у водителя
(`consumed_at='driver'`) → ошибка (на складе его нет).
3. `already_clean` при открытом clean → `ready_clean` (регрессия на старое
поведение).
4. `addManualClean`: без мешков / без веса / без комментария → ошибки;
count-клиент без штук → ошибка, без веса → ок.
5. Успех: clean-запись с `bags`, `wash_id=''`; событие `storage_manual_clean`
в Log с деталями; у работника — Telegram-уведомление (мок, как в
существующих тестах), у владельца — нет.
6. `storageSummaryByClient_`: ручная запись даёт `clean=1` и `cleanBags` из
записи; запись со стиркой — мешки стирки (регрессия).
7. Ручная запись не попадает в `getDayReport`/`getSummaryReport` как
производство (кг/стирки дня не меняются).
8. `getDayList`: карточка несёт `storage` с цифрами клиента (dirty, clean,
clean_kg, clean_items, clean_bags); у клиента без записей — нули.

## Критерии приёмки

- Подтвердить «Есть чистое бельё» при пустом складе нельзя ни с сервера, ни
(в норме) из UI; текст ошибки ведёт к ручному внесению.
- Работник и владелец могут внести чистое вручную; мешки/вес/комментарий
обязательны; действие подписано в Log и (от работника) уходит владельцу в
Telegram.
- Внесённое чистое видно на складе и у водителя с правильным числом мешков;
для записей из стирок ничего не изменилось.
- Ручная запись не влияет на отчёты производства, смену и payroll.
- В модалке проверки склада до выбора вердикта видны цифры по учёту: кг/шт/
  мешки чистого и число грязных партий; то же у карточек «Осталось со вчера».
- Все тесты выше зелёные; существующие тесты не сломаны.

## Что НЕ входит

- **Биллинг.** Ручное чистое не попадает в счёт: счёт строится по стиркам, а
это бельё либо было постирано и оплачено раньше, либо досистемное.
- **Состав по типам белья.** Склад оперирует `items_total`; per-type разбивки
у складских записей нет и здесь не появляется.
- **Удаление/правка ошибочно внесённой записи.** Сейчас пути нет вообще
(`deleteWash` не покрывает — нет `wash_id`). Если понадобится — отдельный
мини-тикет; до него ошибка исправляется через БД.
- Перенос валидации на `no_dirty` (предупреждение «на складе есть грязное»).
Безвредно, не тратим время.

## Оценка

1,5 дня с тестами. Порядок коммитов: часть 4 (схема + helper) → часть 1
(валидация) → часть 3 (API + эффекты) → часть 5 (серверная проброска цифр) →
часть 2 и UI (модалки).
