# R9. Углубление: одна команда забора чистого водителем

> Выборочный забор чистого на экране водителя — клиентский цикл атомарных вызовов:
> `for (const v of sel) await takeSelMut.mutateAsync([v.id, 'take_clean'])`
> (`client/src/app/driver/page.tsx:376`). Каждая точка — отдельный HTTP-вызов
> `driverAction`; серверной операции «забор по списку точек» нет. Отвал сети на
> 3-й точке из 5 = 2 точки взяты, 3 нет, и для системы это «нормальное» состояние.
> При этом серверный массовый забор `driverTakeAllClean` (`server/deliveries.js:278-297`)
> тоже не атомарен: цикл мультизаписей (Склад + Визит на каждую точку) обёрнут
> в `withLock_`, который является no-op (см. отчёт, кандидат 5).
>
> Углубление: за шов уходит одна команда «взять чистое по списку визитов» в одной
> транзакции. Оба входа — выборочный забор (новый метод `driverTakeClean`) и массовый
> (`driverTakeAllClean`) — вызывают её. Клиентский цикл исчезает.

## Принятые решения (контекст)

- **Новый API-метод `driverTakeClean(token, visitIds)`**, а не расширение
  `driverTakeAllClean`. «Все за дату» и «вот конкретные точки» — два разных входа
  с разными аргументами; общее у них — команда за швом, а не сигнатура метода.
- **Семантика best-effort, как у `driverTakeAllClean`**: точка без чистого на складе
  пропускается, это не ошибка. Ответ: `{ taken, bags, skipped }`. Жёсткий вариант
  «всё или ничего» отклонён: водитель в поле, отметивший 5 точек, из-за одной пустой
  не должен уезжать ни с чем. Атомарность здесь про *сбои записи*, а не про
  бизнес-пропуски.
- **Перенос, не переписывание.** Тело цикла `driverTakeAllClean` переезжает в команду
  как есть; `takeCleanForVisit_` (`server/deliveries.js:240-257`) не меняется — он уже
  пишет `visit_id` в складские записи (R4).
- **Один шаг = один коммит**, `npm test` (server) зелёный после каждого серверного
  шага, `npm run lint` + `npm run build` (client) — после клиентского.
- Транзакционная граница — как принято в R4: вся бизнес-операция = один
  `db.transaction_`, визиты пишутся внутри него же.

## Шаги (один шаг = один коммит)

1. **Команда `takeCleanForVisits_(visits, laundryId)`** в `server/deliveries.js`.
   Чистый перенос тела цикла из `driverTakeAllClean`: для каждого визита —
   `takeCleanForVisit_` (пропуск при `null`), `db.updateRow_(SHEETS.DELIVERIES, ...)`,
   подсчёт taken/bags/skipped. Команда возвращает `{ taken, bags, skipped }`,
   транзакцию не открывает — её открывает вызывающий.
2. **`driverTakeAllClean` на команду.** Метод находит подходящие визиты дня
   (текущий фильтр: `date`, `status === 'planned'`, `!clean_taken_at`), открывает
   `db.transaction_` и вызывает команду. `withLock_` здесь уходит — это последний
   нетранзакционный мультизаписывающий вход в забор чистого. Поведение и формат
   ответа `{ taken, bags }` не меняются (добавляется `skipped`, клиент его не читает —
   допустимо, поле добавочное).
3. **Новый метод `driverTakeClean(token, visitIds)`** в `server/deliveries.js`:
   роль driver/owner, резолв визитов по ids через `findTenantVisit_`
   (чужой/несуществующий id — пропуск, не ошибка: список пришёл с клиента и мог
   устареть), фильтр `status === 'planned' && !clean_taken_at`, затем
   `db.transaction_(команда)`. `logEvent` — одно событие `take_clean_batch`
   со списком id и итогами. Регистрация в `server/api.js`: роль рядом с
   `driverTakeAllClean` (`api.js:75`), диспатч рядом с `api.js:128`.
4. **Тесты сервера**, новый файл `server/test/driver-take-clean.test.js` по образцу
   `driver-return-clean.test.js`:
   - забор по списку из 2–3 точек: складские записи помечены `consumed_at='driver'`
     и `visit_id` своего визита, визиты получили `clean_taken_at`/`clean_bags`;
   - точка без чистого — в `skipped`, остальные взяты;
   - чужой id / закрытый визит — пропущены, не ошибка;
   - атомарность: исключение посередине (подмена `db.updateRow_` бросает на второй
     записи) → ни одна складская запись и ни один визит не изменены;
   - регрессия `driverTakeAllClean`: старые тесты (`api.test.js`, `wash.test.js`)
     зелёные без правок.
5. **Клиент.** В `client/src/app/driver/page.tsx` цикл (строка 376) заменяется на
   одну мутацию `useApiMutation<{ taken: number; bags: number; skipped: number }>('driverTakeClean', { invalidate: 'operational' })`
   с аргументом-массивом id отмеченных точек. Итоговый тост — из ответа
   («Взято: N точек, M меш. ✓» + «пропущено: K» при `skipped > 0`). Локальный
   `selBusy` уходит — используется `isPending` мутации, как у соседних диалогов.
   Имена методов в `useApiMutation` — `string` (`hooks/use-api.ts:246`), отдельной
   регистрации типа не требуется.

## Тесты и проверки

- `npm test` в `server/` — зелёный, включая новый `driver-take-clean.test.js`.
- `npm run lint` и `npm run build` в `client/` — зелёные.
- `npm run test:e2e` в `client/` — существующие сценарии водителя зелёные
  (UI чеклиста не меняется, меняется только транспорт).
- Ручная проверка: водитель отмечает 3 точки → один сетевой запрос
  `driverTakeClean` (видно в DevTools), а не три `driverAction`.

## Критерии приёмки

- Выборочный забор — один вызов API, одна серверная транзакция на весь список.
- `driverTakeAllClean` и `driverTakeClean` делят команду `takeCleanForVisits_`;
  расхождений в логике маркировки склада между ними нет по построению.
- Сбой посередине пакета не оставляет частично взятых точек (тест атомарности).
- Точки без чистого пропускаются и отражаются в ответе, а не валят весь забор.

## Оценка

~1 день: сервер (шаги 1–4) — полдня с тестами, клиент (шаг 5) — пара часов.

## Зависимости и отложено

- **Опирается на R4**: `takeCleanForVisit_` уже пишет `visit_id`, `driverAction`
  уже транзакционный — команда собирается из готовых частей.
- **Что НЕ входит:**
  - Остальные места с `withLock_` no-op (кандидат 5 в целом) — здесь закрывается
    только забор чистого; глобальная замена `withLock_` на транзакции — отдельный
    разбор, если решим его делать.
  - Stringly-typed имена методов в `useApiMutation` (кандидат 11) — R9 добавляет
    ещё одну строку-имя, типизацию имён это не чинит и не ухудшает.
  - UI выборочного забора (чеклист, диалог подтверждения) не меняется.
