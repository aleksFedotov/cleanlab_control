# R8. Углубление: одна модалка на действие со стиркой (разрыв форков ×2)

> Рефакторинг с **точечным исправлением дрейфа**. Четыре бизнес-действия
> домена «Стирка» реализованы парами разошедшихся модалок
> (74–133 строки каждая, интерфейс ≈ половина реализации — shallow):
>
> - **StartWashModal** — `app/(dashboard)/wash/[id]/` ↔ `app/worker/`.
>   Дрейф: подсказка «Отобрать до взвешивания: {piece_types}» есть только
>   у работника; лейбл «(необязательно)» — только в карточке; версия
>   карточки на RHF+zod, worker-версия на голом `useState`.
> - **StorageCheckModal** — `wash/[id]/` ↔ `worker/`. Близнецы, различие —
>   навигация после снятия стирки; карточка тянет `ManualCleanModal` из
>   чужого раздела (`@/app/worker/ManualCleanModal`).
> - **DeferWashModal** — `report/` ↔ `wash/[id]/`. Дрейф: report-версия в
>   обход `useApiMutation` — голый `useMutation` + `api()` +
>   `getSession()?.token` + ручная инвалидация `OPERATIONAL_PREFIXES`
>   (report/DeferWashModal.tsx:45-55).
> - **EditWashModal** — `report/` (131) ↔ `wash/[id]/` (98). Глубокая
>   развилка: report-версия сама грузит типы (`useRefs`) и строит `counts`
>   из `wash.items`; версия карточки получает `counts`/`totalQty` пропсами
>   (несохранённые правки степперов карточки, wash/[id]/page.tsx:604-606);
>   zod-схемы разные (`z.number()` vs `z.string()` + парсинг).
>
> Фоновая хрупкость: `worker/page.tsx:26-28` и `storage/page.tsx:23`
> импортируют модалки из чужих разделов `app/` — кросс-раздельные
> зависимости уже есть, но бессистемные. Выносим модалки действий со
> стиркой в `components/wash/` — по одной на действие; различия контекста —
> пропсы, мутации — только `useApiMutation`.

## Принятые решения (контекст)

- **Дрейф чинится при выносе** (наследуем правило R7): единая
  StartWashModal получает piece_types-подсказку и лейбл «(необязательно)»
  на обоих экранах; единая схема форм — react-hook-form + zod (конвенция
  проекта, worker-вариант на `useState` — выброс).
- **EditWashModal: опциональный `initialCounts`.** Модалка сама грузит
  типы через `useRefs` и по умолчанию строит `counts` из `w.items`;
  карточка передаёт `initialCounts`/`initialTotal` с несохранёнными
  правками степперов, отчёт — нет. Один компонент, два контекста.
- **Валидация веса/мешков: строки + парсинг** (`z.string()` + `parseFloat`
  с заменой запятой при сабмите, как в версии карточки и legacy) — ввод
  «12,5» продолжает работать; report-версия (`z.number()`) переезжает на
  это. Сознательное изменение: сообщения валидации «Не отрицательное» из
  отчёта исчезают — неотрицательность обеспечивается парсингом
  (`|| 0`, как legacy).
- **Все мутации — через `useApiMutation`**: ручные `useMutation` + `api()`
  + инвалидация `OPERATIONAL_PREFIXES` в report-модалках удаляются
  (invalidate: 'operational' — тот же эффект одной строкой).
- **Тип пропса — узкий структурный** (`{ id, status, wash_date,
  dirty_weight_kg, bags, items?, piece_types? }`), а не `DayWash`/
  `ReportWash`: модалке не важно, из какого ответа пришла стирка.
- **Дом — `components/wash/`** (прецедент — `components/payroll/`).
  Туда же переносятся de facto общие, но не форкнутые: `ManualCleanModal`
  (потребители: storage/page, обе StorageCheckModal), `AddWashModal` и
  `ShiftCloseDialog` (потребители: wash/page, worker/page). После тикета
  ни один раздел `app/` не импортирует компоненты из чужого раздела.
- **Навигационные различия — пропсы, не копии**: StorageCheckModal
  принимает `onRemoved` (карточка: `router.push('/wash')`; работник:
  не передаёт — остаётся на экране); StartWashModal/DeferWashModal —
  опциональный `onDone`.
- **Перенос маленькими коммитами**: одна модалка = один коммит; после
  каждого `npm run lint` и `npm run build` зелёные.

## Шаги (один шаг = один коммит)

### Шаг 1. `components/wash/StartWashModal`

- База — версия карточки (RHF+zod); добавить piece_types-плашку из
  worker-версии (показывать при `w.piece_types?.length`); лейбл веса —
  «Вес грязного белья, кг (необязательно)»; опциональный `onDone`.
- `wash/[id]/page.tsx` и `worker/page.tsx` — на импорт из
  `@/components/wash/StartWashModal`; обе старые версии удаляются.

### Шаг 2. `components/wash/StorageCheckModal` + `ManualCleanModal`

- `ManualCleanModal` переносится как есть в `components/wash/` (три
  потребителя из двух разделов — de facto общий).
- StorageCheckModal: база — любая из копий; различие навигации —
  пропс `onRemoved` (см. «Принятые решения»); обе старые версии и
  алиас-импорт `@/app/worker/ManualCleanModal` удаляются.

### Шаг 3. `components/wash/DeferWashModal`

- База — версия карточки (`useApiMutation('deferWash',
  { invalidate: 'operational' })`); `onDone` опционален (отчёт не
  передаёт — остаётся в таблице; карточка — назад на доску; работник —
  как сейчас, через версию карточки).
- report-версия с ручной мутацией удаляется; `report/page.tsx` — на общий
  импорт.

### Шаг 4. `components/wash/EditWashModal`

- Единая модалка по решениям выше: `useRefs` внутри, `counts` из
  `w.items` по умолчанию, опциональные `initialCounts`/`initialTotal`,
  `z.string()` + парсинг с запятой, `useApiMutation('editWashData', …)`.
- Карточка передаёт свои несохранённые `counts`/`total`; отчёт — только
  `wash`. Обе старые версии удаляются.

### Шаг 5. Переезд de facto общих модалок

- `AddWashModal`, `ShiftCloseDialog` — перенос как есть в
  `components/wash/`; импорты в `wash/page.tsx` и `worker/page.tsx`
  правятся. Поведение не меняется.
- После шага: `grep -r "app/(dashboard)" app/worker app/(dashboard)/storage`
  по импортам компонентов пуст; worker не знает про раздел дашборда.

## Тесты и проверки

- Unit-тестового раннера в клиенте нет — не вводим (конвенция проекта,
  как в R7). Проверки: `npm run lint` и `npm run build` после каждого шага.
- **Ручной прогон 8 сценариев** (4 действия × 2 контекста): «В работу» из
  карточки и у работника (у обоих — piece_types-плашка); проверка склада
  из карточки (снятие → доска) и у работника (остаёмся, «Начать стирку»);
  перенос из отчёта и из карточки; правка из отчёта (counts из items) и
  из карточки (counts из степперов, после сохранения карта обнуляется).

## Критерии приёмки

- Один файл на действие: `StartWashModal`, `StorageCheckModal`,
  `DeferWashModal`, `EditWashModal` существуют в единственном экземпляре —
  в `components/wash/`; форков в `app/` нет.
- В модалках стирки нет прямых `useMutation`/`api()`/`getSession()` —
  только `useApiMutation`; ручная инвалидация `OPERATIONAL_PREFIXES`
  из report-модалок удалена.
- Разделы `app/` не импортируют компоненты друг из друга (worker и
  storage — только из `@/components/…`).
- Подтверждённый дрейф устранён: piece_types-подсказка на обоих экранах;
  ввод веса с запятой работает в обеих EditWashModal-контекстах.
- `npm run lint` и `npm run build` зелёные; 8 ручных сценариев пройдены.

## Оценка

1–1,5 дня: шаги 1–3 — по 1–2 ч, шаг 4 — 2–3 ч (самая глубокая развилка),
шаг 5 — 1 ч, ручной прогон — 1–2 ч.

## Зависимости и отложено

- Зависимостей от R3–R7 нет; тикет самодостаточен. С R7 соседствует
  (оба про клиентскую раскладку стирки), конфликтов по файлам нет.
- **Что НЕ входит** (отдельные решения, здесь не делать):
  - **Кандидат 11 — глобальная инвалидация кэша**: `OPERATIONAL_PREFIXES`
    как blunderbuss (10 ключей на любую мутацию) и stringly-typed имена
    методов. Здесь убираем только ручные обходы `useApiMutation` в
    report-модалках, саму модель инвалидации не трогаем.
  - `CompleteWashModal`, `EditDoneWashModal`, `NumInputModal`,
    `IssueDateModal`, `AddItemTypeModal` — не форкнуты, живут в своих
    разделах; переезд — только если появится второй потребитель.
  - Визуальный редизайн форм; содержимое модалок (поля, тексты) кроме
    перечисленного дрейфа не меняется.
