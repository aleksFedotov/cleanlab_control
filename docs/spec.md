# CleanLab Control (Прачка360) — Спецификация MVP

> Источник требований: карта проекта в Obsidian `Projects/CleanLab Control` (модель данных, жизненный цикл стирки, роли и доступ, экраны сотрудника/владельца/TV, отчёты, стек, roadmap). Файлы Obsidian не изменяются; данный документ — рабочая спецификация для реализации.

## 1. Назначение

Система учёта стирок в прачечной: владелец вечером выставляет развоз на завтра → сотрудник в цеху взвешивает грязное бельё, стирает, пересчитывает чистое по позициям, завершает стирку → в конце дня закрывает смену (всё завершено или перенесено) → владелец получает итоги в веб-отчёте и Telegram-дайджесте (кг и детализация по позициям).

**Роли:** владелец (`OWNER_PIN`, веб + Telegram), сотрудник (`WORKER_PIN`, общий планшет в цеху), табло цеха (TV, секретная ссылка, только чтение).

## 2. Стек и архитектура

- **Google Apps Script (GAS)**, привязанный к одной Google Таблице. Один проект.
- `SpreadsheetApp` — БД; `HtmlService` — SPA (`Index.html`) и табло (`Tv.html`); `UrlFetchApp` — Telegram Bot API; `ScriptApp` — триггеры (fallback-дайджест, бэкап); `CacheService` — сессии и кэш справочников; `PropertiesService` — секреты; `LockService` — блокировки записи; `DriveApp` — бэкап.
- Клиент: vanilla HTML/CSS/JS, вызовы через `google.script.run`. Без фреймворков.
- Локальная разработка: `clasp` (push/deploy), исходники в `src/`, Node-тесты ядра в `tests/`.
- Часовой пояс: `Europe/Moscow` в `appsscript.json`; все даты/«сегодня»/timestamps — только `Session.getScriptTimeZone()`, никаких `new Date()` на клиенте для даты смены.

## 3. База данных (одна Google Таблица, 7 листов)

Форматы: даты `yyyy-MM-dd`, время `HH:mm`, вес — десятичное с точностью 0,1 кг.

### 3.1 `Settings` (A=key, B=value)
`WEB_APP_URL`, `DIGEST_TIME` (напр. `21:30`), `LAUNDRY_NAME`, `SCHEMA_VERSION` (начиная с `1`). Скрипт сверяет `SCHEMA_VERSION` при старте; смена схемы = новая версия + функция-миграция.

### 3.2 Секреты — Script Properties (не таблица)
`BOT_TOKEN`, `OWNER_PIN`, `WORKER_PIN`, `WEBHOOK_SECRET`, `TV_KEY`, `OWNER_CHAT_ID`.

### 3.3 `Clients`
`id` (`cli_<n>`), `name`, `contact`, `address`, `type` (`отель`/`ресторан`/`спа`/`прочее`), `storage` (`да`/`нет`), `active` (`да`/`нет`), `comment`.

### 3.4 `ItemTypes`
`id` (`itm_<n>`), `name`, `sort` (int), `active` (`да`/`нет`).
Стартовое наполнение: пододеяльник, простыня, наволочка, полотенце банное, полотенце для рук, полотенце для ног, халат, скатерть, салфетка, покрывало, прочее.

### 3.5 `Washes`
`id` (`wash_<n>`), `client_id`, `wash_date`, `issue_date`, `status` (`planned`/`in_progress`/`done`/`stored`/`issued`/`cancelled`), `dirty_weight_kg`, `items_total` (денормализованная сумма `WashItems.qty`, пишется под тем же локом), `comment`, `created_by` (`owner`/`worker`), `created_at`, `started_at`, `done_at`, `issued_at`, `deferred_from` (дата последнего переноса, только UI-признак), `deferred_reason`.

Семантика дат: `wash_date` — день плана цеха (перенос = изменение этого поля); `issue_date` — день выдачи. Обычная стирка: `issue_date = wash_date + 1`. Правило статуса при завершении: `issue_date > wash_date + 1` → `stored`, иначе → `done`.

Сортировка списка дня: `wash_date = <дата> AND status NOT IN (issued, cancelled)`; сначала незавершённые (`planned`, `in_progress`) в порядке постановки, затем завершённые.

### 3.6 `WashItems`
`id` (`wi_<n>`), `wash_id`, `item_type_id`, `qty` (int). Создаются только при завершении стирки; `qty=0` не пишется.

### 3.7 `Shifts`
`id` (`shift_<n>`), `date` (уникальна), `status` (`open`/`closed`), `opened_at` (первое действие сотрудника — смена создаётся автоматически, upsert по дате), `closed_at`, `total_kg`, `washes_done`, `washes_deferred`, `digest_sent` (bool).

### 3.8 `Log`
`ts`, `actor` (`owner`/`worker` — роль, не человек), `action`, `entity`, `details` (JSON/текст, старое → новое).
MVP-события: `wash_create`, `wash_start`, `wash_done`, `wash_issue`, `wash_defer`, `wash_cancel`, `wash_edit`, `shift_close`.

### 3.9 Требования к выборкам
Журнальные листы (`Washes`, `WashItems`, `Log`) никогда не читаются целиком (`getDataRange()` запрещён): выборки «снизу вверх», последние N строк (актуальные даты в хвосте). Архивация прошлых лет не должна ломать запросы. Масштаб: ~20 стирок/день.

## 4. Жизненный цикл стирки

### 4.1 Переходы
- `planned → in_progress`: сотрудник «В работу» + вес грязного (`started_at`, `dirty_weight_kg`).
- `in_progress → done|stored`: пересчёт чистого + «Завершить стирку»; статус по правилу дат (§3.5).
- `done|stored → issued`: владелец «Выдано» (`issued_at`). Финальный статус.
- `planned → cancelled`: владелец «Отменить» в развозе. Строка не удаляется; из списка дня исчезает; закрытие не блокирует.
- Перенос (`planned`/`in_progress`): не статус, а смена `wash_date`; `deferred_from` = дата, с которой переносим (последний перенос), `deferred_reason`; вес и статус сохраняются; событие `wash_defer` в `Log` (полная цепочка переносов — по журналу).
- Перенос из `partial` (достирка остатка): стирка возвращается в `planned` на новую дату, `issue_date = новая wash_date + 1`; вес/пересчёт постиранной части сохраняются (её clean-запись остаётся на складе, остаток при повторном завершении добавит вторую). Если открытой dirty-записи склада нет — создаём (остаток грязного в цеху; иначе карточка «Нет белья на складе»). Запланированный визит развоза клиента на старую `issue_date` переносится на новую (`visit_move`, reason `wash_defer`); визит не в `planned` или дубль на целевую дату — не трогаем (`visit_moved: false` в деталях `wash_defer`).

### 4.2 Исправление данных (`wash_edit`)
- У `done`/`stored` кнопка «Изменить данные»: правка веса и/или пересчёта.
- Кто: сотрудник — пока смена этого дня открыта; владелец — всегда.
- Как: строки `WashItems` стирки удаляются и пишутся заново, `dirty_weight_kg` и `items_total` перезаписываются; статус и `done_at` не меняются.
- Снимок `Shifts.total_kg` после закрытия смены **не** пересчитывается.
- Каждая правка — `wash_edit` в `Log` (старое → новое).

### 4.3 Склад чистого белья
У клиента `storage=да` → владелец ставит дальнюю `issue_date`; при завершении → `stored`; видна в разделе «Склад»; в день `issue_date` появляется в секции «Выдать сегодня»; «Выдано» → `issued`. Правка `issue_date` у `stored` (и у `done`, пока не выдана) статус не меняет. Складская стирка закрытие смены не блокирует.

### 4.4 Блокировка закрытия смены
Блокируют: `wash_date = сегодня AND status IN (planned, in_progress)`. Не блокируют: `done`, `stored`, `issued`, `cancelled`, перенесённые. При блокировке — список незавершённых с действиями «Завершить» / «Перенести».

## 5. Роли и доступ

### 5.1 Вход
- Одна PIN-форма. `login(pin)` сверяет с `OWNER_PIN`/`WORKER_PIN` из Script Properties → роль `owner`/`worker`.
- Сессия: случайный токен (UUID) → `{role, exp}` в `CacheService`, TTL ~12 ч, скользящее продление при каждом запросе. Токен в `localStorage` клиента.
- Каждая серверная функция принимает токен первым параметром; роль — только из сессии, параметру `role` от клиента сервер не доверяет.
- Истечение сессии → клиент показывает PIN-форму, несохранённые данные на экране не теряются. Явный выход = отзыв токена.

### 5.2 Матрица прав
| Действие | owner | worker |
|---|---|---|
| Список дня, вес/пересчёт/завершение, перенос, внеплановая стирка, закрытие смены | ✅ | ✅ |
| Правка веса/пересчёта завершённой | ✅ всегда | ✅ пока смена дня открыта |
| Изменить `issue_date` у `done`/`stored` | ✅ | ❌ |
| Развоз на завтра, «Выдано», отчёты за любой день, справочники | ✅ | ❌ |
| Telegram-дайджест | получает | — |

### 5.3 Табло цеха
Секретный URL `?tv=1&key=<TV_KEY>`, без PIN, только чтение; сервер отдаёт только агрегаты дня; функций записи для TV нет.

## 6. Серверное API (черновой состав, уточняется в тикетах)

- `doGet(e)`: `?tv=1&key=<TV_KEY>` → `Tv.html`; иначе → `Index.html`.
- `doPost(e)`: только Telegram webhook; проверка `?secret=<WEBHOOK_SECRET>` и/или заголовка `X-Telegram-Bot-Api-Secret-Token`; неверный секрет — молчаливый 200.
- `login(pin)` → `{token, role}`; `logout(token)`.
- Сотрудник: `getDayList(token, date)`, `startWash(token, washId, weightKg)`, `saveCount(token, washId, items)` (черновой пересчёт на клиенте, сохранение при завершении), `completeWash(token, washId, items)`, `editWashData(token, washId, weightKg, items)`, `deferWash(token, washId, newDate, reason)`, `addUnplannedWash(token, clientId, comment)`, `closeShift(token)`, `getShiftCloseState(token)`.
- Владелец (дополнительно): `getDeliveryPlan(token, date)`, `addToDelivery(token, clientId, washDate, issueDate, comment)`, `cancelWash(token, washId)`, `markIssued(token, washId)`, `updateIssueDate(token, washId, issueDate)`, `getStorage(token)`, `getDayReport(token, date)`, CRUD справочников `saveClient/deleteClient(архив)/saveItemType`.
- TV: `getTvData(key)` — минимальный JSON: счётчики дня + стирки текущей даты (клиент, статус, кг, штук, пометка переноса, комментарий).
- Все функции записи — под `LockService.getScriptLock()`; перед записью перечитывается текущий статус, невалидный переход отклоняется (идемпотентность: повторное «Завершить» не дублирует `WashItems`, повторное «В работу» не затирает `started_at`). Много-листовые записи — одна функция под одним локом.

## 7. Веб-приложение

### 7.1 Общие требования UI цеха
Крупные кнопки/шрифт (работа в перчатках), цифровая клавиатура (вес шаг 0,1; количество −/+), один экран = одно действие, сохранение на каждом шаге. Потеря связи никогда не проходит молча: красная плашка «Нет связи — данные НЕ сохранены», значения остаются на экране; сохранённым считается только подтверждённое сервером. На время запроса кнопка блокируется, спиннер с текстом («Сохраняем…», «Завершаем…»).

### 7.2 Экран сотрудника
- **Список дня** (главный): шапка (название, дата с переключателем ‹ ›, «Закрыть смену»); карточки стирок (клиент крупно, тип, чип статуса «К стирке»/«В работе»/«Готово»/«На складе»/«Перенесена с <дата>», вес и штук по мере ввода, «выдача <issue_date>» для складских, комментарий); фильтры «Все / К выполнению / Готово»; «+ Добавить стирку» (внеплановая, `created_by=worker`).
- **Карточка стирки**: шапка (клиент, дата выдачи, комментарий, «Перенести»). Шаг 1 — «В работу» → вес (шаг 0,1, быстрые +1/+5, если вес уже был — показать сохранённый) → «Сохранить вес». Шаг 2 — пересчёт: список активных типов по `sort`, −/qty/+, живой итог «Всего: N шт». Шаг 3 — «Завершить стирку» → подтверждение (клиент, вес, позиции, итог) → «Подтвердить» → тост «Стирка завершена ✓» (для складской: «бельё на склад»).
- **Перенос**: «Завтра»/«Послезавтра»/календарь + причина (необязательно).
- **Закрытие смены**: если незавершённые — красный блок со списком (кнопки «Завершить»/«Перенести»), «Закрыть смену» неактивна; если чисто — итоги («Постирано X кг · Завершено Y · Перенесено Z»), подтверждение, после закрытия экран «Смена закрыта в <время>», список дня доступен на просмотр.

### 7.3 Экран владельца (все экраны сотрудника плюс)
- **Развоз на завтра**: секция «Постирать завтра» — активные клиенты с «+ В развоз» (`issue_date` по умолчанию = завтра+1, для `storage=да` подсказка «складской клиент» и правка даты, комментарий); ниже — поставленные стирки с «Отменить» (только `planned`). Секция «Выдать завтра» — стирки с `issue_date = завтра` в `done`/`stored` (клиент, кг, штук, адрес), «Выдано»; просроченные выдачи подсвечены сверху.
- **Склад**: `stored`-стирки по клиентам (кг, штук, позиции, дата выдачи), сортировка по `issue_date`, просроченные подсвечены, «Выдано» из списка, правка `issue_date`.
- **Отчёт за день**: переключатель даты, сводка (кг, завершено/перенесено/отменено/на складе/выдано, статус смены), детальная таблица (клиент, вес, позиции «название ×qty», штук, начата, завершена, статус), незавершённые — внизу; «Изменить данные» из строки завершённой в любой момент.
- **Клиенты**: список, добавление/редактирование, архивация (`active=нет`).
- **Типы белья**: список с `sort`/активностью, добавление/переименование/выключение; удаление запрещено, если тип встречается в `WashItems`.

### 7.4 TV-табло (`Tv.html`)
Тёмная тема, очень крупный шрифт (читается с 3–5 м). Шапка: название, дата, часы. Счётчики: «Всего / К стирке / В работе / Готово / На складе / Перенесено». Карточки стирок дня сеткой 2–4 колонки (клиент крупно, цветной чип статуса — серый/жёлтый/зелёный/синий, вес, штук, «перенесена с <дата>», комментарий мелко). Порядок: «В работе» → «К стирке» → «Готово»/«На складе». Автополлинг `getTvData()` каждые 30–60 сек; индикатор «данные на HH:mm»; при потере связи — последние данные + красная плашка. Без скролла до ~16 карточек.

## 8. Отчёты

### 8.1 Каналы
Полный веб-отчёт (основной, раздел владельца, любой день) + краткий Telegram-дайджест.

### 8.2 Агрегаты (единый принцип — день плана `wash_date`)
- Кг за день: `SUM(dirty_weight_kg)` по `wash_date = дата` и статусам `done`/`stored`/`issued`.
- Перенесено: события `wash_defer` в `Log` с исходной датой = дата (корректно для цепочек переносов).
- Отменено: `wash_date = дата AND status = cancelled`.
- На складе: `status = stored` на момент отчёта.
- Выдано: `issued_at` внутри даты.
- Снимок `Shifts` — на момент закрытия; веб-отчёт пересчитывает живые данные.

### 8.3 Telegram-дайджест
- Отправка: (1) сразу после `shift_close`; (2) fallback — time-trigger в `DIGEST_TIME`, если смена не закрыта (пометка «⚠ Смена ещё не закрыта» + список незавершённых). Когда смену всё же закроют после fallback — повторный дайджест не шлётся, только «Смена закрыта в HH:mm ✓».
- Защита от дубля: один `LockService`; под локом «проверить `digest_sent` → отправить → записать флаг»; флаг пишется только после HTTP 200 от Bot API.
- Формат: шапка «📊 Прачка360 — итоги <дата>», кг и стирки, перенесено (с датами), склад, выдано, детали по стиркам одной строкой каждая, строка о закрытии смены. Пустой день: «За <дата> стирок не было».

## 9. Telegram webhook

- `doPost` — только webhook; идемпотентен по `update_id` (Telegram шлёт ретраи).
- Использование: `/start` → бот просит PIN; любое сообщение, равное `OWNER_PIN` → фиксация `OWNER_CHAT_ID` (формат `/start <PIN>` также поддерживается); исходящий дайджест.
- Ответ 200 быстро, короткая обработка апдейта.

## 10. Канбан «Неделя» (планирование выдачи)

- Вкладка «Неделя» у владельца: 7 колонок (Пн–Вс), карточка = одна выдача чистого белья клиенту (`issue_date`).
- Цикл: стирка за день до выдачи (`wash_date = issue_date − 1`) — дневные задачи работников подтягиваются из `wash_date` без изменений дневного вида.
- Материализация прошлой недели: `getWeekPlan` под локом, если неделя пустая (нет не-cancelled стирок с `wash_date`/`issue_date` внутри), один раз копирует прошлую неделю как planned-стирки со сдвигом +7 дней (`week_copy` в `Log`). Повторные вызовы не дублируют.
- Действия (owner, под локом): `addWeekCard` (выдача в день X → стирка X−1), `moveWeekCard` (только planned; сдвигает обе даты), `removeWeekCard` (отмена planned, делегирует `cancelWash`).
- UI: перенос тап-диалогом по дням недели (без drag&drop), добавление «+» в колонке, не-planned карточки — только просмотр.

## 11. Надёжность и эксплуатация

- `LockService` на все записи (вес, пересчёт, завершение, перенос, закрытие, upsert смены). Идемпотентность переходов (перечитывание статуса). Атомарность много-листовых записей. Клиент блокирует кнопку до ответа.
- Кэш: `Settings`, `Clients`, `ItemTypes` в `CacheService` (TTL ~5 мин), сброс при записи в эти листы. Записи не кэшируются.
- Бэкап: ежедневный time-trigger, `DriveApp.makeCopy` в папку `Прачка360/backups`, имя с датой, хранить последние 30.
- Триггер fallback-дайджеста: `ScriptApp.newTrigger` на `DIGEST_TIME`, ежедневно.
- Bootstrap: функция `setup()` создаёт листы, заголовки, стартовые `ItemTypes`, `Settings` (`SCHEMA_VERSION=1`) — идемпотентна.

## 12. Тестирование

Node-тесты чистой бизнес-логики (ядро без GAS-зависимостей): переходы статусов и отклонение невалидных, правило `done`/`stored` по датам, перенос (сохранение веса, цепочки в `Log`), блокировка закрытия смены, агрегаты отчёта (вкл. перенесённые/отменённые/выданные), сортировка списка дня, идемпотентность повторных действий. GAS-сервисы мокируются. Тонкий GAS-слой и UI — ручная проверка после деплоя.

## 13. Деплой (чек-лист, детали в docs/deploy.md)

1. `clasp login`, создание проекта GAS, привязанного к новой таблице; `clasp push`.
2. Script Properties: `BOT_TOKEN`, `OWNER_PIN`, `WORKER_PIN`, `WEBHOOK_SECRET`, `TV_KEY` (+ `OWNER_CHAT_ID` пишется ботом).

## 14. Вне объёма MVP (post-MVP, из roadmap)

Финансы/CRM, поимённый штат и сдельная зарплата, аналитика по клиентам, вес чистого белья, расходники, несколько машин/постов, уведомления клиентам, QR/штрихкоды, фото до/после, мультисменность, полный аудит, ротация и звук табло. Сознательно не берём: поштучная детализация изделий, квитанции B2C, роль оператора, SMS.

**Финансы — только авторасчёт счетов (тикет P2 в `docs/tickets.md`)**: кнопка «Счёт за месяц» по клиенту — документ с пунктами: кг постирано, позиции по типам белья (кол-во × цена), итог. Тарификация настраивается per-клиент: цена за кг + исключения по типам белья поштучно (напр. халаты). Данные уже есть в стирках и `WashItems`. Остальное из финансов/CRM не берём. клиенты (30–40, B2B) заходят по логину/паролю (scrypt-хеш, токен-сессии, роль `client`) и вносят заявки на забор — позиции белья и число мешков. Водитель подтверждает забор, цех видит ожидаемое, владельцу видны расхождения «заявлено/факт». Доступы заводит владелец, саморегистрации нет.
