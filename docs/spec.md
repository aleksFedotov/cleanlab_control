# CleanLab Control (Прачечная PRO) — Спецификация

> Рабочая спецификация текущей системы. Платформа: VPS-бэкенд (`server/`, Node/Express + SQLite). Google Apps Script-версия удалена; история переезда — в `docs/vps-migration.md`.

## 1. Назначение

Система учёта стирок в прачечной: владелец планирует развозы → водитель привозит грязное бельё и развозит чистое → сотрудник в цеху взвешивает, стирает, пересчитывает чистое по позициям, завершает стирку → в конце дня закрывает смену → владелец получает итоги в веб-отчёте и Telegram-дайджесте (кг, позиции, мешки).

Система **мультитенантная**: одна установка обслуживает несколько прачек (tenant = прачка). Все операционные данные разделены по `laundry_id`; владелец видит все прачки и переключается между ними.

**Роли:** владелец (`owner`, веб + Telegram, все прачки), сотрудник (`worker`, планшет в цеху), водитель (`driver`, маршрут развоза), клиент (`client`, задел под кабинет — аккаунт создаётся, вход пока не настроен). Табло цеха (TV) — секретная ссылка, только чтение.

## 2. Стек и архитектура

- **Node.js + Express + better-sqlite3**, один процесс (`server/`). Снаружи — Caddy reverse_proxy с авто-HTTPS.
- SQLite — БД (`server/data/cleanlab.sqlite`, WAL). Таблицы исторически повторяют листы Google-таблицы, все значения хранятся TEXT (даты — строками формата схемы).
- Фронтенд: vanilla HTML/CSS/JS, статика из `server/public/` (`index.html`, `tv.html`); вызовы API — `fetch` на `POST /api/<method>`, тело `{args: [...]}`. Без фреймворков.
- Сессии — в памяти процесса (`Map` в `server/auth.js`), TTL 12 ч, скользящее продление.
- Кэш справочников (Settings/Clients/ItemTypes) — в памяти, TTL 5 мин, сброс при записи; ключи кэша per-tenant.
- Блокировки: `LockService` не нужен — однопроцессный Node + синхронный better-sqlite3; функция-заглушка `withLock_` сохранена для читаемости.
- Telegram: webhook `POST /telegram/webhook?secret=<WEBHOOK_SECRET>`, исходящие — через `fetch` к Bot API. Fallback-дайджест — по расписанию на VPS (см. `fallbackDigestTrigger`).
- Часовой пояс: `APP_TZ` (по умолчанию `Europe/Moscow`), все даты/«сегодня» — через `server/util/time.js`, никаких `new Date()` на клиенте для даты смены.
- Конфигурация — ENV (`server/config.js`, локально `node --env-file=.env index.js`).

## 3. База данных (SQLite, таблицы = `HEADERS` в `server/schema.js`)

Форматы: даты `yyyy-MM-dd`, время `HH:mm`, вес — десятичное с точностью 0,1 кг. `SCHEMA_VERSION = 2`.

### 3.1 Мультитенантность
- `Laundries`: `id`, `name`, `active` (`да`/`нет`).
- `laundry_id` есть у таблиц `Washes`, `Shifts`, `Deliveries`, `Storage`, `Clients`, `Log`, `Settings`. Пустой `laundry_id` в `Settings` = глобальная настройка, per-tenant строка её перекрывает (per-tenant: `LAUNDRY_NAME`, `OWNER_CHAT_ID`, `TV_KEY`).
- `WashItems` и `ItemTypes` без `laundry_id`: тенант определяется через `wash_id`, справочник типов белья глобальный.
- Прачка берётся из сессии (`session.laundryId`); все чтения/записи операционных таблиц фильтруются по ней — строка чужой прачки для API «не существует».

### 3.2 `Settings` (`key`, `value`, `laundry_id`)
Глобально: `DIGEST_TIME` (напр. `21:30`), дефолтный `LAUNDRY_NAME`. Per-tenant: `LAUNDRY_NAME`, `TV_KEY`, `OWNER_CHAT_ID`.

### 3.3 Секреты — ENV (`server/.env`, см. `.env.example`)
`BOT_TOKEN`, `WEBHOOK_SECRET`, `TV_KEY`, `TV_KEY_2`, имя первой прачки (`LAUNDRY_NAME`), логин/пароль владельца (`OWNER_LOGIN`, `OWNER_PASSWORD` — upsert в Users при каждом старте), опционально `LAUNDRY2_NAME`. `OWNER_CHAT_ID` в ENV не нужен — бот пишет его в Settings per-tenant.

### 3.4 `Clients`
`id` (`cli_<n>`), `name`, `contact`, `address`, `type` (`отель`/`ресторан`/`спа`/`прочее`), `storage` (`да`/`нет`), `active`, `comment`, `item_types` (JSON-массив id типов белья клиента, пусто = все), `accounting` (`weight`/`count`/`both`, пусто = both), `laundry_id`.

### 3.5 `ItemTypes`
`id` (`itm_<n>`), `name`, `sort` (int), `active`. Справочник глобальный. Стартовое наполнение: пододеяльник, простыня, наволочка, полотенце банное, полотенце для рук, полотенце для ног, халат, скатерть, салфетка, покрывало, прочее.

### 3.6 `Washes`
`id` (`wash_<n>`), `client_id`, `wash_date`, `issue_date`, `status`, `dirty_weight_kg`, `items_total`, `bags` (мешков после стирки — по ним водитель сверяет выдачу), `comment`, `created_by` (`owner`/`worker`/`auto`), `created_at`, `started_at`, `done_at`, `issued_at`, `deferred_from`, `deferred_reason`, `laundry_id`.

Статусы: `planned`, `no_linen` (грязного нет — подтверждено проверкой склада), `in_progress`, `partial` (частичная стирка), `ready_clean` (чистое уже на складе — подтверждено проверкой), `done`, `stored`, `issued`, `cancelled`.

Семантика дат: `wash_date` — день плана цеха (перенос = изменение этого поля); `issue_date` — день выдачи. Обычная стирка: `issue_date = wash_date + 1`. Правило статуса при завершении: `issue_date > wash_date + 1` → `stored`, иначе → `done`.

Сортировка списка дня: `wash_date = <дата> AND status NOT IN (issued, cancelled)`; сначала незавершённые, затем завершённые. Список дня автоформируется из развоза на завтра (`ensureWashesFromDelivery_`): клиент в развозе на date+1 → плановая стирка сегодня, идемпотентно (отменённые тоже считаются существующими).

### 3.7 `WashItems`
`id` (`wi_<n>`), `wash_id`, `item_type_id`, `qty` (int). Создаются при завершении стирки; `qty=0` не пишется.

### 3.8 `Shifts`
`id` (`shift_<n>`), `date` (уникальна в прачке), `status` (`open`/`closed`), `opened_at` (смена создаётся автоматически при первом действии, upsert по дате), `closed_at`, `total_kg`, `washes_done`, `washes_deferred`, `digest_sent` (`да`/пусто), `laundry_id`.

### 3.9 `Deliveries` (визиты развоза)
`id` (`del_<n>`), `date`, `client_id`, `ord`, `status` (`planned`/…/закрыт), `delivered_at`, `pickup`, `driver_comment`, `created_by`, `created_at`, `clean_taken_at`, `clean_bags`, `picked_at`, `dirty_handed_at`, `pickup_only` (`да` — только забрать грязное), `laundry_id`. Логика — `server/deliveries.js`.

### 3.10 `Storage`
`id`, `client_id`, `kind` (`dirty`/`clean`), `weight_kg`, `items_total`, `wash_id`, `created_at`, `consumed_at`, `laundry_id`. Грязное создаётся водителем при сдаче, расходуется при «В работу»; чистое — при завершении стирки, расходуется при выдаче.

### 3.11 `Log`
`ts`, `actor` (роль), `action`, `entity`, `details` (JSON/текст), `laundry_id`.
События: `wash_create`, `wash_start`, `wash_done`, `wash_issue`, `wash_defer`, `wash_cancel`, `wash_edit`, `wash_delete`, `shift_close`, `storage_check`, `visit_move`, `week_copy`, `user_create`, `user_deactivate` и события водителя.

### 3.12 `Users`
`id` (`usr_<n>`), `laundry_id` (пусто у owner), `name`, `role` (`owner`/`worker`/`driver`/`client`), `pin` (устаревшее, не используется), `active`, `client_id` (у `client` — ссылка на Clients), `login` (глобально уникален), `pass_hash` (scrypt, формат `salt:hash` в hex).

### 3.12.1 `Sessions`
`token` (UUID), `user_id`, `laundry_id` (активная прачка сессии), `expires_at` (unix-мс). См. §5.1.

### 3.13 Требования к выборкам
Журнальные таблицы (`Washes`, `WashItems`, `Log`) не читаются целиком: выборки «с хвоста» (`ORDER BY rowid DESC LIMIT N`, по умолчанию 500). Чтения/записи — через tenant-варианты (`readTailByTenant_`, `findRowsByTenant_`, `appendRowTenant_`). `readAll_` — только справочники и миграции. Масштаб: ~20 стирок/день на прачку.

## 4. Жизненный цикл стирки

### 4.1 Переходы
- `planned → in_progress`: сотрудник «В работу» (опционально вес грязного); dirty-запись склада расходуется, смена создаётся автоматически.
- `in_progress → done|stored|partial`: вес чистого (обязателен, кроме клиентов с `accounting=count`) + количество мешков (обязательно) + пересчёт; статус по правилу дат (§3.6); `mode='partial'` — частичная стирка (чистая часть на складе, клиент не готов к выдаче). Результат — clean-запись склада.
- `done|stored → issued`: владелец «Выдано» (`issued_at`). Финальный статус; clean-запись склада расходуется.
- `planned → cancelled`: владелец «Отменить». Строка не удаляется; из списка дня исчезает; закрытие не блокирует.
- Удаление (`deleteWash`, owner): ошибочно созданная невыданная стирка удаляется вместе с позициями и складскими строками; `issued` удалять нельзя.
- Проверка склада (`confirmStorageCheck`, planned/no_linen): `no_dirty` → `no_linen`; `already_clean` → `ready_clean`; `has_dirty` → стирка остаётся/возвращается в `planned`, при отсутствии создаётся dirty-запись.
- Перенос (`planned`/`in_progress`/`partial`): не статус, а смена `wash_date`; `deferred_from` = дата последнего переноса, `deferred_reason`; событие `wash_defer` в `Log`. Из `partial`: возврат в `planned`, `issue_date = новая wash_date + 1`, постиранная часть сохраняется; при отсутствии dirty-записи создаётся; визит развоза переносится следом (`visit_move`, только planned и без дубля на целевую дату).

### 4.2 Исправление данных (`wash_edit`)
- У завершённой — правка веса, пересчёта и мешков (`editWashData`).
- Кто: сотрудник — пока смена этого дня открыта; владелец — всегда.
- Как: `WashItems` удаляются и пишутся заново, вес/`items_total`/`bags` перезаписываются; статус и `done_at` не меняются; открытая clean-запись склада правится синхронно.
- Снимок `Shifts.total_kg` после закрытия смены **не** пересчитывается. Каждая правка — `wash_edit` в `Log`.

### 4.3 Склад чистого белья
У клиента `storage=да` → владелец ставит дальнюю `issue_date`; при завершении → `stored`; видна в разделе «Склад»; «Выдано» → `issued`. Правка `issue_date` у `stored`/`done` статус не меняет. Складская стирка закрытие смены не блокирует.

### 4.4 Блокировка закрытия смены
Блокируют: `wash_date = сегодня AND status IN (planned, in_progress)`. Закрытие возможно с `force=true`; при этом владельцу в Telegram уходит предупреждение о незавершённых (перенести их может только владелец) и список не готовых к завтрашнему развозу (причины: `washing_incomplete`, `partial`, `no_clean`).

## 5. Роли и доступ

### 5.1 Вход
- Экран входа: логин + пароль, без выбора прачки — прачка определяется учётной записью. `login(username, password)` ищет активного пользователя по глобально уникальному логину; пароль хранится как scrypt-хэш `salt:hash` (hex), сравнение — `timingSafeEqual` (`util/passwords.js`). На все ошибки входа — одно сообщение «Неверный логин или пароль». Rate-limit: 5 неудачных попыток по логину → блок на 5 минут (счётчик в памяти процесса).
- Роль `client`: аккаунт создаётся (с `client_id` на клиента справочника), но вход возвращает «Доступ для клиента не настроен».
- Сессия: случайный токен (UUID) → строка таблицы `Sessions(token, user_id, laundry_id, expires_at)` — персистентно (переживает рестарт), TTL 30 дней, скользящее продление при каждом запросе, протухшие строки чистятся при старте и входе. Сессия читается из БД с join Users; деактивация пользователя обесценивает его сессии. Токен в `localStorage` клиента.
- У owner `laundry_id` пуст; активная прачка сессии (`Sessions.laundry_id`) на входе — первая активная, переключается `switchLaundry(token, laundryId)` (в UI — переключатель прачек, список приходит в ответе `login`).
- Каждый метод API принимает токен первым параметром; роль и прачка — только из сессии, параметрам от клиента сервер не доверяет.
- Истечение сессии → клиент показывает форму входа, несохранённые данные на экране не теряются. Явный выход = удаление строки Sessions.

### 5.2 Матрица прав
| Действие | owner | worker | driver |
|---|---|---|---|
| Список дня, вес/пересчёт/завершение, перенос, внеплановая стирка, закрытие смены, проверка склада | ✅ | ✅ | ❌ |
| Правка веса/пересчёта завершённой | ✅ всегда | ✅ пока смена дня открыта | ❌ |
| Изменить `issue_date`, «Выдано», отмена/удаление стирки, отчёты, справочники, неделя | ✅ | ❌ | ❌ |
| Маршрут развоза, подтверждение забора/выдачи | ✅ | ❌ | ✅ |
| Пользователи (`listUsers`/`createUser`/`deactivateUser`), `switchLaundry` | ✅ | ❌ | ❌ |
| Telegram-дайджест | получает (per-tenant чат) | — | — |

### 5.3 Табло цеха
Секретный URL `/tv.html?key=<TV_KEY>` (ключ per-tenant, из Settings), без PIN, только чтение; сервер отдаёт только агрегаты дня той прачки; функций записи для TV нет.

## 6. Серверное API

Монтирование: каждая публичная функция → `POST /api/<method>`, тело `{args: [...]}` (`server/api.js`, `mountApi`). Ответ `{ok: true, ...}` / `{ok: false, error}`.

- Публичные (без токена): `login`, `getTvData(key)`.
- Auth: `login(username, password)`, `logout(token)`, `switchLaundry(token, laundryId)`.
- Сотрудник: `getDayList(token, date)`, `startWash`, `completeWash(token, washId, items, weightKg, mode, bags)`, `editWashData`, `deferWash`, `addUnplannedWash`, `getShiftCloseState`, `closeShift(token, force)`, `confirmStorageCheck`.
- Владелец: `getDeliveryPlan`, `addToDelivery`, `cancelWash`, `deleteWash`, `markIssued`, `updateIssueDate`, `getWeekPlan`, `addWeekCard`, `moveWeekCard`, `removeWeekCard`, `getStorage`, `getDayReport`, справочники (`saveClient`, `deleteClient`, `saveItemType`, `rememberClientItemType`, `getRefs`), пользователи (`listUsers`, `createUser`, `resetUserPassword`, `deactivateUser`, `makeTelegramBindCode`), прачки (`listLaundries` — с TV-ключами, `createLaundry` — с генерацией TV-ключа, `deactivateLaundry` — нельзя отключить активную прачку сессии и последнюю активную).
- Водитель/развозы (`server/deliveries.js`): `getDeliveryVisits`, `addDeliveryVisit`, `moveDeliveryVisit`, `removeDeliveryVisit`, `setPickupOnly`, `getDriverRoute`, `driverTakeAllClean`, `driverAction`, `driverHandover`.
- TV: `getTvData(key)` — счётчики дня + стирки текущей даты прачки (клиент, статус, кг, штук, перенос, комментарий).
- Telegram: `POST /telegram/webhook?secret=<WEBHOOK_SECRET>`; неверный секрет — молчаливый 200.
- Идемпотентность: перед записью перечитывается текущий статус, невалидный переход отклоняется (повторное «Завершить» не дублирует `WashItems`, повторное «В работу» не затирает `started_at`).

## 7. Веб-приложение

### 7.1 Общие требования UI цеха
Крупные кнопки/шрифт (работа в перчатках), цифровая клавиатура (вес шаг 0,1; количество −/+), один экран = одно действие, сохранение на каждом шаге. Потеря связи никогда не проходит молча: красная плашка «Нет связи — данные НЕ сохранены», значения остаются на экране; сохранённым считается только подтверждённое сервером. На время запроса кнопка блокируется, спиннер с текстом.

### 7.2 Экран сотрудника
Список дня (шапка: название прачки, дата ‹ ›, «Закрыть смену»; карточки с чипами статусов и пометками склада; фильтры; «+ Добавить стирку»), карточка стирки (в работу → вес → пересчёт по типам (с учётом `item_types`/`accounting` клиента) → мешки → завершить с подтверждением), перенос, «Изменить данные», закрытие смены (блокировка/force + итоги + «не готовы к развозу»).

### 7.3 Экран владельца (все экраны сотрудника плюс)
Переключатель прачек в шапке. Развоз (план на день, выдачи, просроченные), Склад (stored-стирки + записи dirty/clean/частичные остатки), Отчёт за день (сводка + детальная таблица + правка), Канбан «Неделя», справочники Клиенты (с `item_types` и `accounting`) и Типы белья (удаление запрещено, если тип встречается в `WashItems`), экран «Сотрудники» (список пользователей прачки, создание аккаунтов owner/worker/driver/client с проверкой глобальной уникальности логина, сброс пароля, привязка Telegram по коду, деактивация).

### 7.4 Экран водителя
Маршрут на день (`getDriverRoute`): забрать чистое со склада (мешки), визиты с подтверждением выдачи/забора грязного, комментарий; сдача грязного в цех (`driverHandover` → dirty-записи склада).

### 7.5 TV-табло (`tv.html`)
Тёмная тема, очень крупный шрифт (3–5 м). Шапка: название прачки, дата, часы. Счётчики: «Всего / К стирке / В работе / Готово / На складе / Перенесено». Карточки дня сеткой 2–4 колонки. Порядок: «В работе» → «К стирке» → «Готово»/«На складе». Автополлинг `getTvData()` каждые 30–60 сек; индикатор свежести; при потере связи — последние данные + красная плашка.

## 8. Отчёты

### 8.1 Каналы
Полный веб-отчёт (раздел владельца, любой день, per-tenant) + краткий Telegram-дайджест.

### 8.2 Агрегаты (единый принцип — день плана `wash_date`)
- Кг за день: `SUM(dirty_weight_kg)` по `wash_date = дата` и статусам `done`/`stored`/`issued`.
- Перенесено: события `wash_defer` в `Log` с исходной датой = дата.
- Отменено: `wash_date = дата AND status = cancelled`.
- На складе: `status = stored` на момент отчёта.
- Выдано: `issued_at` внутри даты.
- Снимок `Shifts` — на момент закрытия; веб-отчёт пересчитывает живые данные.

### 8.3 Telegram-дайджест (per-tenant)
- Отправка: (1) сразу после `closeShift`; (2) fallback — `fallbackDigestTrigger` в `DIGEST_TIME` по всем активным прачкам, если смена не закрыта (пометка «⚠ Смена ещё не закрыта» + список незавершённых). Позднее закрытие после fallback — только «Смена закрыта в HH:mm ✓».
- Защита от дубля: «проверить `digest_sent` → отправить → записать флаг»; флаг пишется только после HTTP 200 от Bot API.
- Чат получателя — `OWNER_CHAT_ID` из per-tenant Settings.

## 9. Telegram webhook

- `POST /telegram/webhook?secret=<WEBHOOK_SECRET>`; неверный секрет — молчаливый 200; идемпотентен по `update_id` (ретраи Telegram, Map в памяти, TTL 24 ч).
- Привязка чата владельца: одноразовый 6-значный код (экран «Сотрудники» → `makeTelegramBindCode`, TTL 10 мин, код привязан к активной прачке владельца). Сообщение с кодом (или `/start <код>`) фиксирует `OWNER_CHAT_ID` той прачки; неверный/протухший код — ответ «Неверный или просроченный код». `/start` без кода подсказывает, где взять код.
- Ответ 200 быстро; отправка сообщений — async `fetch` к Bot API.

## 10. Канбан «Неделя» (планирование развоза)

- Вкладка «Неделя» у владельца: 7 колонок (Пн–Вс), карточка = визит развоза (`Deliveries`) клиента в день D. Дневной план цеха формируется из развоза на завтра (§3.6).
- Материализация прошлой недели: `getWeekPlan`, если неделя пустая, один раз копирует прошлую неделю как planned-визиты со сдвигом +7 дней (`week_copy` в `Log`). Повторные вызовы не дублируют.
- Действия (owner): `addWeekCard`, `moveWeekCard` (только planned), `removeWeekCard`.
- UI: перенос тап-диалогом по дням недели, добавление «+» в колонке, не-planned карточки — только просмотр.

## 11. Надёжность и эксплуатация

- Однопроцессный Node + синхронный better-sqlite3: записи атомарны без явных локов. Идемпотентность переходов (перечитывание статуса). Клиент блокирует кнопку до ответа.
- Кэш справочников TTL 5 мин, сброс при записи; ключи per-tenant.
- Бэкап SQLite: копия файла БД по cron на VPS (стратегия — в `docs/vps-migration.md`, открытые вопросы).
- Миграция-сид `migrateToV2_` (`server/db.js`): при пустой `Laundries` все существующие данные → прачка 1, per-tenant Settings (`LAUNDRY_NAME`, `TV_KEY`), пользователи из ENV (owner + worker/driver прачки 1; вторая прачка — только если задан `LAUNDRY2_NAME`, её настройки и пользователи из `LAUNDRY2_*`/`TV_KEY_2`). Срабатывает один раз.
- Дальше прачки заводятся из UI: вкладка «Прачки» владельца → `createLaundry` (TV-ключ генерируется случайно, кладётся в per-tenant `Settings.TV_KEY`); `deactivateLaundry` — архивация без удаления данных.
- Bootstrap `setup()` (`server/setup.js`): таблицы, стартовые `ItemTypes`, дефолтные Settings — идемпотентен; таблицы создаются и при старте сервера.

## 12. Тестирование

Node-тесты (`node --test`) в `server/test/`: чистое ядро (`core.test.js`), слой SQLite (`db.test.js`), API на SQLite in-memory (`api.test.js`), Telegram (`telegram.test.js`), мультитенантность (`tenancy.test.js`). Запуск: `npm test` (из корня — проксирует в `server/`).

## 13. Деплой (чек-лист, детали в docs/deploy.md)

1. VPS: Node LTS, Caddy (`reverse_proxy localhost:3100`), домен + авто-HTTPS.
2. `server/.env` из `.env.example`: `BOT_TOKEN`, `LAUNDRY_NAME`, `OWNER_LOGIN`/`OWNER_PASSWORD`, `WEBHOOK_SECRET`, `TV_KEY`/`TV_KEY_2`.
3. Запуск: `node --env-file=.env index.js` (systemd/PM2, автоперезапуск).
4. Telegram `setWebhook` на `https://<домен>/telegram/webhook?secret=<WEBHOOK_SECRET>`; владелец генерирует код привязки на экране «Сотрудники» и отправляет его боту.
5. TV-ссылки: `/tv.html?key=<TV_KEY>` для каждой прачки.

## 14. Вне объёма (roadmap)

Финансы/CRM, поимённый штат и сдельная зарплата, аналитика по клиентам, расходники, несколько машин/постов, уведомления клиентам, QR/штрихкоды, фото до/после, мультисменность, полный аудит, ротация и звук табло. Сознательно не берём: поштучная детализация изделий, квитанции B2C, роль оператора, SMS.

**Финансы — только авторасчёт счетов (тикет P2 в `docs/tickets.md`)**: кнопка «Счёт за месяц» по клиенту — документ с пунктами: кг постирано, позиции по типам белья (кол-во × цена), итог. Тарификация per-клиент: цена за кг + исключения по типам белья поштучно.

**Клиентский портал (тикет P1, частично подготовлено)**: роль `client` в `Users` уже существует (аккаунт с `client_id`, вход пока закрыт). Далее: вход клиента, заявки на забор (позиции + мешки), подтверждение водителем, расхождения «заявлено/факт». Саморегистрации нет.
