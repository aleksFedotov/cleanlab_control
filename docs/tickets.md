# Пост-MVP

## P1. Клиентский портал: заявки на забор белья
Контекст: 30–40 клиентов (гостиницы и т.п.) сами вносят накладные — сколько мешков и какого белья сдают. Водитель видит заявки, подтверждает забор («забрал 3 мешка»). Цех заранее знает, что приедет. Расхождение «заявлено vs фактически принято» видно владельцу.

- **Аутентификация клиентов** (VPS-ветка `server/`): таблица `client_users` (client_id, login, password_hash, salt), хеширование `crypto.scrypt` (stdlib, без новых зависимостей), сессии токеном в таблице `sessions` (как PIN-сессии, но после логина паролем). Rate-limit на логин (5 попыток → пауза). Роль `client` рядом с owner/worker/driver; PIN-логин сотрудников не трогаем.
- **Управление доступами**: владелец заводит клиента в «Справочниках» (логин + сгенерированный пароль), сброс пароля владельцем, смена пароля самим клиентом. Саморегистрации нет (B2B).
- **Страница клиента**: форма заявки — позиции по типам белья из справочника + количество, число мешков, дата, комментарий; список своих заявок со статусами.
- **Таблица `intake_requests`**: клиент, позиции, мешки, статусная модель `заявлено → подтверждено водителем → принято в цехе`, факт приёмки вводит сотрудник, расхождение заявлено/факт.
- **Экран водителя**: заявки на сегодня, подтверждение «забрал N мешков» — заявка превращается в забор. **Экран цеха**: «ожидается N мешков от клиента X».
- Оценка: 4–6 дней (бэкенд: несколько методов API + 2–3 таблицы; фронт: одна страница + доработка экранов водителя/цеха; Node-тесты на auth и статусы).

## P2 (расширенный). Финансы: прайс и авторасчёт счетов клиентам

Контекст: единственный интерес из spec §14. Кнопка «Счёт за период» у клиента — документ со строками: сколько кг постирано, поштучные позиции, рейсы, подъёмы, итоги по ценам. Правила зафиксированы по живым счетам (примеры в разделе тестов — они же эталонные сценарии).

### Принятые решения (контекст)

- **В биллинге участвует только вес грязного.** Партия взвешивается один раз при
  приёмке в цех; чистый вес в счётах не используется вообще. Строка «кг» в счёте =
  `Σ Washes.dirty_weight_kg` — как в отчётах (spec §8.2).
- **Поштучное отбирают до взвешивания.** Халаты/шторы/одеяла физически не попадают
  в вес партии → двойного счёта нет, эталонные веса типов не нужны.
- **Рейс тарифицируется по ногам.** У визита 0–2 ноги: забор грязного (`picked_at`)
  и доставка чистого (`delivered_at`). Ярус ноги («менее 30 кг») определяется
  **весом грязного партии**; обе ноги одного цикла автоматически получают один
  ярус: приняли 29 кг → забор и отправка оба «менее 30 кг» с доплатой.
- **Подъём на этаж вводит водитель — номером этажа.** При подтверждении визита он
  указывает, на какой этаж поднимался (3-й, 4-й, …); пусто/1/2 — без доплаты,
  доплачивается всё выше 2-го этажа. Подъём — не на каждом рейсе (в счётах: 15
  подъёмов при 18 рейсах) и не свойство клиента.
- **Номенклатура счёта отделена от `ItemTypes`.** Несколько типов белья
  схлопываются в одну позицию счёта («Подушка, Одеяло, Наматрасник — 6 шт»);
  у позиции есть код НФ для 1С. Коды хранятся per-tenant: общие — дублируются,
  свои — различаются.
- **Цены двухуровневые:** дефолтный прайс прачки + переопределения клиента
  (55 ₽/кг у одного, 75 ₽/кг у другого; халат 100 ₽ vs 155 ₽).

### Схема (SCHEMA_VERSION → 4, все значения TEXT, как принято)

#### Новая таблица `BillingItems` (номенклатура счёта, per-tenant)

```
id (bi_<n>), laundry_id, name, unit, kind, oneway, max_kg, per_floor, ext_code, sort, active
```

- `name` — как в счёте («Услуги прачечной (Халат)», «Доставка менее 30 кг»).
- `unit`: `кг` | `шт` | `рейс` | `этаж`.
- `kind`: `wash_weight` | `wash_pcs` | `trip` | `lift`.
- `oneway` = `да` — позиция для визита с одной ногой («Доставка в одну сторону/Забор»).
- `max_kg` — верхняя граница яруса веса ноги (у «менее 30 кг» → `30`; пусто — без яруса).
- `per_floor` (только `kind=lift`): `да` — цена за каждый этаж выше 2-го
  (3-й этаж = 1 шт, 4-й = 2 шт); пусто — цена за факт подъёма (визит = 1 шт).
  Какой режим — по договору с клиентом; флаг позволяет оба.
- `ext_code` — код номенклатуры 1С (НФ-00000007), опционально.
- На прачку — ровно одна активная позиция `wash_weight` (весовая по умолчанию).

Стартовое наполнение по счетам: Постельное бельё (кг), Халат (шт), Подушка/Одеяло/
Наматрасник (шт), Штора (шт), Доставка (рейс), Доставка менее 30 кг (рейс, max_kg=30),
Доставка в одну сторону/Забор (рейс, oneway=да), Подъём на этаж (lift; per_floor —
по договору: за этаж выше 2-го или за факт подъёма).

#### Новая таблица `ClientTariffs`

```
id (trf_<n>), client_id, billing_item_id, price, laundry_id
```

- `client_id` пусто → дефолт прачки; строка клиента перекрывает дефолт.
- Upsert по (client_id, billing_item_id); `price=''` — снять переопределение.

#### Новая таблица `ClientItemBilling` (per-клиентская привязка типов к позициям счёта)

```
id (cib_<n>), client_id, item_type_id, billing_item_id, laundry_id
```

Зачем: один и тот же тип у разных клиентов считается по-разному (полотенце:
у отеля — в кг, у фитнес-зала — поштучно). `ItemTypes` — справочник глобальный,
поэтому различие живёт на уровне клиента.

Цепочка разрешения привязки для позиции пересчёта:
1. строка `ClientItemBilling` этого клиента → её `billing_item_id`
   (пустое значение = «у этого клиента тип идёт в вес», даже если глобально
   тип привязан к штучной позиции — например, халат в кг);
2. нет строки → `ItemTypes.billing_item_id` (дефолтная привязка);
3. и та пуста → весовая позиция по умолчанию.

Upsert по (client_id, item_type_id); удаление строки = вернуться к дефолту.

#### Изменения существующих таблиц

- `ItemTypes` + `billing_item_id` (пусто = весовая позиция по умолчанию; ссылка на
  позицию `wash_pcs` — «считается поштучно»).
- `Deliveries` + `lift_floor` (число строкой, пусто/1/2 = без доплаты) — этаж,
  на который поднимался водитель.

### Правила расчёта (`buildInvoice_`, чистая функция в `core.js`)

```
resolvePrice_(tariffs, clientId, billingItemId) → клиент → дефолт прачки → null
```

**Стирки** (весовая и штучная части):
- Выборка: `status IN (done, stored, issued)`, `wash_date` в [from, to].
  `cancelled` исключены; `partial` исключена (попадёт в счёт при достирке —
  итоги суммируются, как принято в getDayList).
- Весовая строка: `Σ dirty_weight_kg` × цена `wash_weight`-позиции.
- Штучные строки: `WashItems` этих стирок → привязка `item_type → billing_item`
  по цепочке `ClientItemBilling` → `ItemTypes.billing_item_id` → вес;
  qty суммируются по биллинг-позиции (подушка+одеяло+наматрасник → одна строка).
- Позиция без цены (ни у клиента, ни в дефолте) → строка с `price=null`,
  попадает в `missing_prices` — молча не теряем.

**Рейсы** (визиты клиента в периоде, `status NOT IN (cancelled, empty)`):
- Ноги: `picked_at` не пусто → забор; `delivered_at` не пусто → доставка.
- Вес ноги-забора: `Σ weight_kg` dirty-записей Storage клиента с `created_at` в
  дату визита. Вес ноги-доставки: `Σ dirty_weight_kg` стирок, выданных в этот
  визит (та же партия → тот же ярус, что у забора; чистый вес не используем).
- Выбор позиции для ноги:
  1. у визита одна нога и есть `trip`-позиция с `oneway=да`, подходящая по ярусу → она;
  2. иначе первая `trip`-позиция с `max_kg > вес ноги` (по возрастанию max_kg);
  3. иначе `trip`-позиция без `max_kg`.
- Каждая нога = +1 к количеству выбранной позиции.
- Подъём: `lift_floor > 2` на визите → к `lift`-позиции: при `per_floor=да`
  `+(lift_floor − 2)` этажей, иначе `+1` за визит.

**Результат** `getClientInvoice(token, clientId, from, to)`:

```
{ client, from, to,
  lines: [{ billing_item_id, name, ext_code, unit, qty, price, amount }],
  total, missing_prices: [billing_item_id, ...] }
```

### UI

- **Справочники → вкладка «Прайс»**: BillingItems (название как в счёте, единица,
  код НФ, ярус, oneway, per_floor) + дефолтные цены прачки. Услуги полностью
  управляются из UI: добавление/правка/архивация без изменения кода и передеплоя
  (сценарий «добавить матрас»: тип белья → позиция прайса → привязка → цена).
  Если позиция уже попадала в счета — только архивация (`active=нет`), удаление
  запрещено, чтобы не ломать историю.
- **Типы белья**: поле «Позиция в счёте» (select из штучных BillingItems).
- **Карточка клиента**: эффективный прайс с пометками «наследовано /
  переопределено» + таблица «как считаются типы у этого клиента»
  (по каждому типу белья: вес или штучная позиция, с возможностью переопределить);
  кнопка «Счёт за период» → документ со строками
  (наименование, код НФ, кол-во, ед., цена, сумма) + итог; print-стили,
  «Сохранить как PDF» из браузера; реквизиты клиента (inn/kpp/legal_address)
  уже есть в карточке — выводим в шапку счёта.
- **Водитель**: при подтверждении визита — ввод этажа подъёма (шаговик «Этаж:
  − 3 +», пусто = лифт/1–2-й этаж, без доплаты). Крупный контрол, по требованиям
  UI цеха.
- **Работник**: плашка в карточке стирки «Отобрать до взвешивания: халаты, шторы»
  (типы, привязанные к штучным позициям, у этого клиента) + бейдж «поштучно»
  в пересчёте — защита от «утопил халаты в килограммах».

### Тесты (`server/test/invoice.test.js`, `node --test`)

- Весовой клиент: Σкг × цена; `cancelled` исключены; `partial` не в счёте до достирки.
- Группировка: подушка+одеяло+наматрасник → одна строка с суммарным qty.
- Per-клиентская привязка: полотенце в кг у отеля и поштучно у фитнес-зала в
  одном периоде; обратный случай — халат по умолчанию поштучный, у клиента X
  переопределён в вес; цена за кг 55 и 75 у разных клиентов одновременно.
- Наследование цены: переопределение → дефолт прачки → `missing_prices`.
- Ярусы: нога 29 кг → «менее 30 кг»; 31 кг → обычная; **доставка наследует ярус
  забора** (приняли 29 кг → обе ноги лёгкие); одна нога → oneway-позиция.
- Подъём: этаж пусто/1/2 → без доплаты; 3-й → 1 шт (per_floor) или за факт;
  4-й → 2 шт (per_floor); не на каждом визите; правка владельцем пересчитывает счёт.
- Права: worker/driver → «Нет доступа».
- Эталон: три счёта из обсуждения воспроизводятся строка в строку:
  - 792 кг × 55 + халат 12 × 100 + подушка/одеяло/наматрасник 6 × 300;
  - 862 кг × 55 + халат 15 × 100 + штора 8 × 200 + «в одну сторону» 4 × 300;
  - 422 кг × 75 + халаты 10 × 155 + «менее 30 кг» 14 × 450 + подъём 15 × 300 +
    «в одну сторону/забор» 4 × 450.

### Отложено сознательно

- Статусы счёта (выставлен/оплачен) — отдельным шагом, если понадобится.
- Несколько весовых позиций у одной прачки («махра за кг дороже постельного») —
  в MVP одна `wash_weight`-позиция; появится потребность — `ItemTypes.billing_item_id`
  уже позволит ссылаться и на весовые позиции (потребуется разделение веса по типам).
