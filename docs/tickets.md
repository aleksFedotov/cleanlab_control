# CleanLab Control — Тикеты MVP

> По `docs/spec.md`. Порядок — по зависимостям. Реализация — строго по одному одобренному тикету за цикл.

## T1. Скелет проекта и тестраннер
- `appsscript.json` (timeZone `Europe/Moscow`, webapp-деплой, oauthScopes), `.clasp.json`-шаблон, `.gitignore`, `package.json` с Node test runner (`node --test`).
- Структура: `src/` (gs/html), `tests/`.
- Критерий: `npm test` запускается (пустой/примерный тест зелёный), структура готова к `clasp push`.

## T2. Слой данных
- `src/Schema.gs`: константы листов/колонок, `SCHEMA_VERSION=1`.
- `src/Setup.gs`: идемпотентная `setup()` — листы, заголовки, стартовые `ItemTypes`, `Settings` (без секретов).
- `src/Db.gs`: чтение «снизу вверх» (последние N строк журнальных листов), append-helpers, генераторы id (`wash_<n>` и т.д.), кэш Settings/Clients/ItemTypes в CacheService (TTL 5 мин, сброс при записи).
- `src/Audit.gs`: запись в `Log`.
- Node-тесты: мок SpreadsheetApp, проверка setup-идемпотентности и выборок с хвоста.

## T3. Ядро бизнес-логики (pure, без GAS)
- `src/Core.gs` (pure functions, общие для GAS и Node): переходы статусов + валидация, правило `done`/`stored` по `issue_date > wash_date + 1`, перенос (сохранение веса/статуса), блокировка закрытия смены, сортировка списка дня, агрегаты отчёта (кг, перенесено по `Log`, отменено, склад, выдано), форматирование дайджеста.
- Node-тесты: все правила из spec §4, §8.2, идемпотентность повторных переходов.

## T4. Серверное API: сессии и функции записи
- `src/Auth.gs`: `login(pin)`, `logout(token)`, сессии в CacheService (TTL 12 ч, скользящее продление), проверка прав по роли.
- `src/Api.gs`: серверные функции из spec §6 (сотрудник + владелец + `getTvData`), каждая — токен первым параметром, записи под `LockService`, перечитывание статуса перед переходом, атомарность `WashItems`+`Washes`, upsert `Shifts` при первом действии, события в `Log`.
- Node-тесты: API поверх моков — права (worker vs owner), идемпотентность, блокировка закрытия.

## T5. SPA: вход и экран сотрудника
- `src/Index.html`: PIN-форма, localStorage-токен, мягкий повторный вход; роутинг по роли.
- Сотрудник: список дня (фильтры, чипы, «+ Добавить стирку»), карточка стирки (вес → пересчёт → завершить с подтверждением), перенос, «Изменить данные», закрытие смены (блокировка + итоги).
- Требования UI цеха: крупные контролы, шаг 0,1, блокировка кнопки со спиннером, красная плашка при потере связи, сохранённые данные не теряются.
- Проверка: ручная, после деплоя.

## T6. SPA: экран владельца
- Развоз на завтра (обе секции, отмена стирки, «Выдано», просроченные), Склад (группировка, правка `issue_date`), Отчёт за день (сводка + детальная таблица + «Изменить данные»), справочники Клиенты и Типы белья (архивация/выключение, запрет удаления используемого типа).
- Проверка: ручная, после деплоя.

## T7. Telegram: webhook и дайджест
- `src/Telegram.gs`: `doPost` (проверка `WEBHOOK_SECRET`/заголовка, молчаливый 200, идемпотентность по `update_id`), `/start` с PIN → `OWNER_CHAT_ID`.
- Отправка дайджеста после `shift_close` и fallback-триггером `DIGEST_TIME`; атомарный `digest_sent` под локом, флаг только после HTTP 200; «Смена закрыта в HH:mm ✓» при закрытии после fallback.
- Node-тесты: формат дайджеста, идемпотентность, защита от двойной отправки.

## T8. TV-табло
- Ветка `doGet` (`tv=1&key=`, неверный ключ → PIN-форма), `src/Tv.html`: тёмная тема, счётчики, сетка карточек, автополлинг 30–60 сек, индикатор свежести, плашка потери связи.
- `getTvData()` — минимальный JSON (уже в T4, здесь — интеграция и страница).
- Проверка: ручная, после деплоя.

## T9. Эксплуатация: бэкап и деплой-чеклист
- `src/Backup.gs`: ежедневная копия таблицы в `Прачка360/backups`, имя с датой, ротация до 30 копий.
- Установка триггеров (функция `installTriggers()`).
- `docs/deploy.md`: полный чек-лист (clasp, Script Properties, setup(), TZ, деплой, setWebhook, триггеры, TV-ссылка, железо табло по варианту A/B).
