# Тикет P1 — клиентский портал: заявка на забор + трекинг

## Контекст

Клиентский портал — давний задел roadmap (spec.md §14): роль `client` в `Users`
уже существует, аккаунт создаётся с привязкой к `Clients.id`, но вход закрыт
(«Доступ для клиента не настроен»). Этот тикет открывает портал в
**MVP-объёме под пилот на одном клиенте** (всего у прачки 40+ клиентов —
после пилота решим, что докручивать).

Две функции портала:

1. **Заявка на забор**: клиент вводит позиции (простыни ×12, наволочки ×14…),
   число мешков и комментарий до приезда водителя.
2. **Трекинг сдачи**: клиент видит, где его бельё — от забора до доставки
   обратно.

Принципиальные решения (зафиксированы с заказчиком):

- **Заявка — ориентир, а не факт.** Финальные цифры (кг, позиции) берутся из
  фактического пересчёта после стирки (`WashItems`), заявленные данные не
  участвуют ни в каких расчётах. Заявка нужна водителю (объём = мешки) и цеху
  (предварительный план загрузки).
- **Пилот = один клиент, но код без хардкода.** Портал включается наличием
  активного аккаунта у клиента, а не флагом под конкретный `client_id`.
- **Двойной канал разрешён.** Визит развоза без заявки — норма (остальные 39
  клиентов заказывают как раньше); заявка без визита — тоже норма (владелец
  привязывает её к визиту или создаёт визит сам).
- **Денег нет.** Счета (P2), тарифы, платная доставка (P11) — вне объёма.
- **Telegram не трогаем.** Уведомлений в MVP нет вообще: владелец видит новые
  заявки бейджем в интерфейсе, клиент сам заходит смотреть трекинг. Push в
  PWA — отдельным этапом после пилота (учесть: iOS отдаёт web-push только
  установленным на домашний экран PWA, iOS 16.4+).

## Принятые решения по доступу

- **Доступ заводится в карточке клиента** (справочник «Клиенты»), а не на
  экране «Сотрудники»: блок «Доступ в портал» — логин, пароль, кнопка
  «Сбросить пароль». Логин глобально уникален — ошибка «такой логин занят»
  показывается при сохранении. Есть активный аккаунт `client` = портал
  включён для этого клиента.
- **Один логин на клиента** (вводит кто угодно на стороне клиента —
  администратор, горничная), но **задел под несколько аккаунтов**: у заявки
  хранится `created_by = user_id`. Автор клиенту не показывается (при одном
  общем логине это бессмысленно), в `Log` — пишется, пригодится при разборе
  «кто вводил».
- **Смена пароля самим клиентом — не в MVP.** Владелец сбрасывает из
  карточки клиента. Если пилот покажет, что это боль — мини-тикет.

## Модель данных

### Новая таблица `Requests` (заявки на забор)

`id` (`req_<n>`), `client_id`, `laundry_id`, `visit_id` (пусто, пока не
привязана к визиту развоза), `desired_date` (желаемая дата забора,
`yyyy-MM-dd`), `bags` (int), `comment`, `status` (`sent` / `picked` /
`closed`), `created_by` (user id), `created_at`, `updated_at`.

- `status`: `sent` — заявка отправлена, правится клиентом; `picked` —
  водитель подтвердил забор по связанному визиту (`picked_at` выставлен),
  правка закрыта; `closed` — стирка завершена, доступен фактический пересчёт.
- Связка заявка → визит → стирка — через `visit_id` и дальше по существующим
  связям (`Deliveries` → `Washes` через ensureWashesFromDelivery_ / складские
  записи). Отдельного `wash_id` в заявке не храним: визит на D+1 порождает
  стирку на D, поиск идёт по клиенту и дате — как в отчётах.
- Одна активная (`sent`) заявка на визит: повторная отправка клиентом — это
  правка существующей заявки, а не новая строка (идемпотентность как везде:
  перечитываем статус, невалидный переход отклоняем).

### Новая таблица `RequestItems`

`id` (`ri_<n>`), `request_id`, `item_type_id`, `qty` (int). `qty=0` не
пишется — как в `WashItems`. При правке заявки позиции удаляются и пишутся
заново — как в `editWashData`.

`laundry_id` в `RequestItems` не нужен: тенант через `Requests.request_id` —
та же схема, что у `WashItems` → `Washes`.

### Существующие таблицы

Меняется только `Users` логикой (не схемой): вход роли `client` открывается.
`HEADERS` дополняется двумя таблицами — авто-ALTER `createTables_`,
миграция данных не нужна. `SCHEMA_VERSION` поднимаем, если принято — как в
P11.

## Клиентская статусная машина (трекинг)

Клиенту показываем 6 статусов, а не внутренние `Washes.status`. Маппинг
(по связке заявка → визит → стирка клиента на соответствующую дату):

| Клиентский статус | Откуда берётся |
|---|---|
| «Заявка принята» | `Requests.status = sent`, визит ещё не исполнен |
| «Водитель направляется» | визит `planned`, дата = сегодня |
| «На пути в прачечную» | у визита есть `picked_at` (водитель подтвердил забор) |
| «В прачечной, в очереди» | стирка `planned` / dirty-запись склада открыта |
| «Стирается» | стирка `in_progress` |
| «Готово, на складе» | стирка `done` / `stored` / `ready_clean` |
| «Направляется к вам» | у визита есть `clean_taken_at` (водитель забрал чистое) |
| «Доставлено» | визит закрыт / стирка `issued` |

Внутренние статусы (`partial`, `no_linen`, `deferred`, `cancelled`) клиенту
не показываем как есть. Особые случаи:

- `no_linen` (грязного не было) — честный статус «Бельё не передано», без
  деталей цеха.
- `partial` — «Стирается (частично)»: клиенту важно, что часть останется.
- перенос (`deferred_from` непуст) — к статусу добавляется пометка «перенесено
  на ‹дата›», новая дата видна в треке.
- отмена — «Сдача отменена» + комментарий владельца, если есть.

## Этапы (каждый этап = один коммит)

Порядок выбран так, чтобы после каждого коммита система была целостной:
серверные этапы идут с тестами, UI — после API, пилотный клиент включается
в самом конце.

### Этап 1 — вход роли `client` + блок доступа в карточке клиента

**Сервер.** `login` пропускает роль `client` (сейчас — «Доступ для клиента
не настроен»). Прачка сессии — `laundry_id` пользователя (у `client` он
всегда заполнен). Существующий middleware ролей: `client` получает доступ
только к методам портала (этапы 2–4), остальное отклоняется по роли — общая
матрица прав уже это умеет.

`saveClient` / новый метод `setClientAccess(token, clientId, login, password)`:
создание/обновление аккаунта `client` с `client_id`, scrypt-хэш, проверка
глобальной уникальности логина (переиспользуем логику `createUser`).
`resetClientPassword(token, clientId)` — тонкая обёртка над
`resetUserPassword`. Отключение доступа = деактивация аккаунта
(`deactivateUser` уже умеет обесценивать сессии).

**UI (владелец).** В карточке клиента — блок «Доступ в портал»: логин,
пароль (генерируется кнопкой, показывается один раз), «Сбросить пароль»,
«Отключить доступ». Ошибка занятого логина — текстом сервера под полем.

**Тесты:** вход client с верным паролем → сессия с `laundry_id` клиента;
вход с чужим/протухшим — отказ; `setClientAccess` с занятым логином →
ошибка; деактивация → старый токен не работает; client не может вызвать
`getDayReport`/`getWeekPlan` (матрица прав).

### Этап 2 — таблицы заявок + серверное API заявок

**Сервер.** `HEADERS` + `createTables_` для `Requests`/`RequestItems`. Методы:

- `clientCreateRequest(token, desiredDate, bags, comment, items)` — создать
  или перезаписать активную заявку (одна `sent` на клиента+дату); позиции
  переписываются целиком.
- `clientGetRequests(token)` — список заявок клиента с позициями и статусами.
- `clientGetRequest(token, requestId)` — одна заявка (чужая → «не
  существует», как во всех tenant-выборках).
- Водительский забор (`driverAction` с подтверждением `picked_at`) по визиту
  с привязанной заявкой → `Requests.status = picked` (правка закрывается).
- Владелец: `getClientRequests(token, date?)` — заявки прачки (для бейджа и
  привязки), `linkRequestToVisit(token, requestId, visitId)`.

Идемпотентность: правка `picked`/`closed` отклоняется; повторное создание
той же заявки не плодит строки (upsert по клиенту+дате в статусе `sent`).

**Тесты:** CRUD заявки; правка после `picked` отклоняется; чужая заявка не
читается и не правится; tenant-изоляция (заявка другой прачки не видна);
`qty=0` не пишется; upsert вместо дублей.

### Этап 3 — клиентский портал: форма заявки

**UI (клиент).** Новый раздел приложения под роль `client` (роутинг по роли
после `login` уже различает owner/worker/driver — добавляется четвёртая
ветка). Мобильный first: вводит горничная с телефона.

- Экран «Новая заявка»: дата забора (ближайший запланированный визит —
  предвыбран), степперы «−/+» по типам белья клиента (учитываем
  `Clients.item_types` — клиент видит только свои виды; справочник общий,
  фильтр как в пересчёте цеха), число мешков, комментарий. Крупные кнопки,
  цифровая клавиатура — культура цехового UI (spec.md §7.1).
- Правка до забора: та же форма с префиллом. После `picked` — read-only.
- Потеря связи — красная плашка «Нет связи — данные НЕ сохранены», значения
  остаются (общее правило UI).
- Список заявок клиента: дата, статус, мешки.

**Тесты (Playwright e2e):** создание заявки с нуля; степперы; правка до
забора; попытка правки после `picked` — read-only; мобильная вёрстка.

### Этап 4 — трекинг + «заявлено/факт»

**Сервер.** `clientGetTrack(token, requestId)` — клиентский статус по
маппингу выше +, если стирка завершена (`closed`), фактический пересчёт из
`WashItems` (позиции и кг). Заявка без визита тоже трекается: статусы до
«В прачечной» просто не наступают.

**UI (клиент).** Карточка сдачи: вертикальный трек статусов (пройденные —
заполнены, текущий — подсвечен), даты событий, после стирки — две колонки
«Заявлено / Постирано» (позиции + кг). До завершения стирки блок факта не
показываем (не нули и не прочерки): «После стирки здесь появится фактический
пересчёт».

**Тесты:** маппинг каждого внутреннего состояния → клиентский статус (включая
`no_linen`, `partial`, перенос, отмену); факт появляется только после
завершения; чужой трек не читается. e2e: проход трека от «Заявка принята» до
«Доставлено».

### Этап 5 — бейдж заявок у владельца + привязка к визиту

**UI (владелец).** Бейдж «Заявки: N новых» в шапке дашборда (поллинг через
существующий TanStack Query-контур, `getClientRequests` из этапа 2). Экран
заявок: список, у заявки без визита — действия «Привязать к визиту» /
«Создать визит» (создаёт planned-визит через существующий
`addDeliveryVisit` + `linkRequestToVisit`). Заявка видна и в карточке
визита развоза (водителю — мешки и позиции как ориентир объёма).

**UI (водитель).** В визите маршрута — блок «Заявка: 3 мешка, позиции»,
read-only. Подтверждение забора автоматически закрывает правку (этап 2).

**Тесты:** бейдж считает только `sent` без просмотра; привязка к визиту;
создание визита из заявки не дублирует planned-визит на ту же дату; заявка
видна в маршруте водителя.

### Порядок коммитов

1. `Этап 1` — вход client + доступ в карточке клиента (сервер + UI + тесты).
2. `Этап 2` — Requests/RequestItems + API заявок (сервер + тесты).
3. `Этап 3` — форма заявки в портале (UI + e2e).
4. `Этап 4` — трекинг и заявлено/факт (сервер + UI + тесты).
5. `Этап 5` — бейдж и привязка у владельца, заявка у водителя (UI + тесты).

После этапа 1 портал уже открыт (вход есть, функций нет — пустой экран с
плейсхолдером); пилотному клиенту доступ выдаём после этапа 4 минимум.

## Критерии приёмки

- [ ] В карточке клиента заводится логин/пароль; занятый логин — понятная
      ошибка; сброс пароля работает.
- [ ] Клиент входит в портал, видит только свои заявки и свои треки.
- [ ] Заявка: позиции по видам белья клиента, мешки, комментарий; правка до
      забора; после забора — read-only.
- [ ] Трекинг показывает 6 клиентских статусов; `no_linen`/`partial`/
      перенос/отмена отображаются понятными формулировками.
- [ ] После стирки — «Заявлено / Постирано» рядом, read-only.
- [ ] Визит без заявки и заявка без визита — оба работают; владелец
      привязывает заявку к визиту.
- [ ] Владелец видит бейдж новых заявок; водитель видит заявку в маршруте.
- [ ] Все серверные тесты и e2e зелёные; tenant-изоляция проверена.

## Что НЕ входит (отдельные этапы после пилота)

- **Push-уведомления в PWA** (клиенту «забрали/готово/едет», владельцу «новая
  заявка»): service worker, Push API, VAPID, подписки per-устройство; iOS —
  только для установленных PWA (16.4+), онбординг «добавьте на экран домой».
- **Деньги**: показ счёта в портале, связка с тарифами (P2) и платной
  доставкой (P11). Блок «Заявлено/Постирано» — задел под финансовую
  прозрачность, суммы добавятся позже.
- **Несколько аккаунтов на клиента** с отображением автора заявки
  (`created_by` уже хранится — миграция не понадобится).
- **Смена пароля самим клиентом.**
- **Внеплановый забор как отдельный флоу** (сейчас — заявка без визита +
  ручная привязка владельцем).
- **Процесс согласования расхождений** «заявлено/факт» (подтверждение обеими
  сторонами) — в MVP расхождение просто видно.
- **Повтор типовой заявки** («как в прошлый раз»), фото проблем, саморегистрация.

## Оценка

3,5–4 дня суммарно: этап 1 — 0,5 дня; этап 2 — 1 день (две таблицы, API,
tenant-тесты); этап 3 — 1 день (новый раздел, степперы, e2e); этап 4 —
0,5–1 день (маппинг статусов — основная сложность: особые случаи); этап 5 —
0,5 дня.
