# R7. Углубление: единая карта «статус стирки → колонка дня» на клиенте

> Рефакторинг с **сознательным исправлением дрейфа**. Правило раскладки
> стирки по колонкам дня размножено inline в трёх страницах, и копии уже
> разошлись (client/src/app):
>
> | статус | `wash/page.tsx:21-35` | `today/page.tsx:44-49` | `worker/page.tsx:200-209` |
> |---|---|---|---|
> | `planned` | К стирке | очередь | очередь |
> | `no_linen` | Готово | **очередь** | Готово |
> | `in_progress` | В работе | в работе | в работе |
> | `done`/`stored`/`partial`/`ready_clean` | Готово | Готово | Готово |
> | `issued` | Готово | **∅ не показывается** | **∅ не показывается** |
>
> Выданная стирка исчезает со страниц «Сегодня» и «Работник» — живой баг;
> `no_linen` — то очередь, то «Готово» в зависимости от экрана. Выносим
> правило в один модуль `client/src/lib/wash-status.ts` с exhaustive-маппингом
> `Record<WashStatus, WashColumn>`: добавление нового статуса в
> `types/api.ts:8-9` без раскладки по колонке ломает компиляцию. Это
> тестовый шов клиента — unit-тестов в проекте нет, дрейф охраняет
> система типов.

## Принятые решения (контекст)

- **Дрейф чинится при выносе, а не консервируется.** В отличие от R6
  (где различие фильтров осознанное), здесь расхождение — признанный баг:
  единая карта, без per-page опций.
- **Единая карта:** `planned` → «К стирке»; `in_progress` → «В работе»;
  `done`, `stored`, `partial`, `ready_clean`, `no_linen`, `issued` →
  «Готово»; `cancelled` → не показывается (`hidden` — сейчас cancelled
  не отображается ни на одном из трёх экранов, поведение сохраняем).
- **`no_linen` единообразно в «Готово»** (как на доске «Стирка» и у
  работника): белья не было, стирка разобрана, действий по ней нет.
  Это меняет страницу «Сегодня»: `no_linen` уходит из очереди в «Готово».
  Связь с P7 («Осталось со вчера» считает `no_linen` незавершённой,
  types/api.ts:204) — серверная логика overdue, колонок не касается,
  не меняется.
- **`issued` появляется в «Готово» на страницах «Сегодня» и «Работник».**
  Следствие на «Сегодня»: `doneKg` (today/page.tsx:50) начнёт включать вес
  выданных стирок — сознательно: выданная стирка постирана, её вес —
  результат дня. Вес `no_linen`-стирок пуст, на `doneKg` не влияет.
- **Модуль — `client/src/lib/wash-status.ts`** (рядом с `dicts.ts`, который
  владеет лейблами/тонами статусов; раскладка по колонкам — доменное
  правило, а не словарь представления, поэтому отдельный файл).
- **Охват — три страницы дня.** `reportGroup` и предикаты
  `canEdit/canDefer/canDelete` отчёта (report/page.tsx:30-46) — другая
  группировка (с измерениями deferred/cancelled), полная и не разошедшаяся;
  не входят, см. «Что НЕ входит».
- **Перенос маленькими коммитами**: модуль → по одной странице за коммит;
  после каждого `npm run lint` и `npm run build` зелёные.

## Шаги (один шаг = один коммит)

### Шаг 1. Модуль `lib/wash-status.ts`

```ts
import type { WashStatus } from '@/types/api';

export type WashColumn = 'todo' | 'doing' | 'done' | 'hidden';

// Единственный источник раскладки статуса стирки по колонкам дня.
// Record<WashStatus, …> — exhaustive: новый статус без раскладки не скомпилируется.
export const WASH_COLUMN: Record<WashStatus, WashColumn> = {
  planned: 'todo',
  no_linen: 'done',
  in_progress: 'doing',
  done: 'done',
  stored: 'done',
  partial: 'done',
  ready_clean: 'done',
  issued: 'done',
  cancelled: 'hidden',
};

export function washColumn(w: { status: WashStatus }): WashColumn {
  return WASH_COLUMN[w.status];
}
```

### Шаг 2. `worker/page.tsx`

- Фильтры колонок (:200-209) заменяются на `washColumn(w) === '…'`.
- Поведение: `issued` появляется в «Готово»; остальное без изменений.
- Поиск по клиенту (:196-199) применяется до раскладки — не трогаем.

### Шаг 3. `today/page.tsx`

- Фильтры (:44-49) на `washColumn`. Поведение: `no_linen` переезжает из
  очереди в «Готово», `issued` появляется в «Готово`; `doneKg` включает
  выданные (см. «Принятые решения»).

### Шаг 4. `wash/page.tsx`

- `COLS` (:21-35) переводится на `washColumn` (match: `washColumn(w) === key`);
  поведение доски не меняется — она уже единственная знает все статусы.

## Тесты и проверки

- Unit-тестовый раннер в клиенте отсутствует (только Playwright e2e) —
  новый не вводим, тестовые файлы не создаём (конвенция проекта).
- **Проверка шва — компилятор**: после шага 1 однократно вручную убедиться,
  что удаление любого ключа из `WASH_COLUMN` даёт ошибку типов
  (`npm run build`), затем вернуть ключ. Автоматизировать не требуется.
- `npm run lint` и `npm run build` зелёные после каждого шага.
- Ручной прогон: на день со стирками в статусах `no_linen` и `issued`
  проверить три экрана — стирки видны в «Готово», счётчики колонок сходятся.

## Критерии приёмки

- Один источник правила «статус → колонка»: в `wash/page.tsx`,
  `today/page.tsx`, `worker/page.tsx` не остаётся inline-перечислений
  статусов для раскладки по колонкам — только `washColumn`.
- `WASH_COLUMN` — exhaustive `Record<WashStatus, WashColumn>`: добавление
  статуса в `WashStatus` без раскладки ломает компиляцию.
- `issued` виден в «Готово» на всех трёх экранах; `no_linen` — в «Готово»
  единообразно; `cancelled` не отображается (как сейчас).
- `npm run lint` и `npm run build` зелёные.

## Оценка

2–3 часа: модуль — 0,5 ч, три страницы — по 0,5 ч, проверки и ручной прогон — 1 ч.

## Зависимости и отложено

- Зависимостей от R3–R6 нет; тикет самодостаточен, чисто клиентский.
- **Что НЕ входит** (отдельные решения, здесь не делать):
  - `reportGroup`, `canEdit`, `canDefer`, `canDelete` (report/page.tsx:30-46) —
    группировка отчёта с измерениями deferred/cancelled; не разошлась.
    Кандидат на переезд в `lib/wash-status.ts` отдельным шагом, если
    появится второй потребитель предикатов.
  - Серверная раскладка и P7-эвристика «Осталось со вчера» (overdue считает
    `no_linen` незавершённой) — не меняется; модель смены — как прежде,
    отдельный пропущенный кандидат.
  - Модалки с развилками по статусам (StorageCheckModal и др.) — кандидат 9
    отчёта, следующая очередь.
