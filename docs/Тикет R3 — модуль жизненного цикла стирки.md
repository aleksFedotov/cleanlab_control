# R3. Углубление: модуль жизненного цикла стирки (`server/wash.js`)

> Рефакторинг без изменения внешнего поведения. После делёжки R1 ядро
> (`server/api/washes.js`, 1018 строк) осталось мелким модулем: ~30 хендлеров
> сами оркестрируют строки БД, склад, смену, аудит и telegram. Таблица переходов
> (`core.js` `TRANSITIONS`) проверяет только `from`-статусы, а все *эффекты*
> переходов живут в телах хендлеров — именно там прячутся баги (серия
> P6/P6.1/P6.2/P7: правки задним числом, откаты склада, «Осталось со вчера»).
> Выделяем глубокий модуль `server/wash.js` — «Стирка» (см. `CONTEXT.md`):
> именные команды домена, каждая владеет своим переходом **и его эффектами**,
> каждая выполняется в настоящей транзакции better-sqlite3.
> HTTP-контракт (`POST /api/<method>`, тело `{ args: [...] }`), имена методов,
> тексты ошибок и поведение фасада не меняются.

## Принятые решения (контекст)

Решения приняты в grilling-сессии архитектурного обзора; не пересматривать без
нового обсуждения.

- **Граница — только стирка из `washes.js`.** Выдача чистого из развоза
  (`deliver_clean`, `undo_deliver`, откаты в `deliveries.js`) в этот заход не
  входит — timestamp-стяжки (`issued_at === delivered_at`) убирает следующий
  тикет (см. «Отложено»).
- **Интерфейс — именные команды домена**, а не generic `transition()`:
  интерфейс говорит на языке домена, фасад и тесты почти не меняются.
- **Эффекты внутри модуля.** Команда сама пишет в Storage/Shifts/Log и шлёт
  telegram через существующие модули (`storage.js`, `core.js`, `audit.js`,
  `telegram.js`). Списки эффектов наружу не возвращаем, инъекцию зависимостей
  не вводим — тестовые швы уже есть (`db._setDbForTests`, стаб
  `globalThis.fetch` в `server/test/helpers/serverMocks.js`).
- **Транзакция на команду.** Новый `db.transaction_()` — тонкая обёртка над
  `better-sqlite3` `db.transaction()`; каждая команда модуля обёрнута в неё.
  `withLock_`-заглушка (`core.js:376`) внутри границы модуля больше не
  используется; сама заглушка остаётся для остального кода.
- **Материализация и кросс-доменная оркестрация — НЕ в модуль** (поправка
  из R5: направление зависимостей `deliveries → wash` односторонне).
  `ensureWashesFromDelivery_` (стирки из визитов) и `addToDelivery` (визит +
  плановая стирка) оперируют обоими доменами и остаются оркестраторами в
  `api/washes.js` — `wash.js` о развозе не знает. Read-эндпоинты
  (`getDayList`, `getDayReport`, …) продолжают вызывать материализацию как
  сейчас. Проблему «чтение пишет в БД» этот тикет не решает (см. «Отложено»).
- **Перенос, не переписывание** (наследуем правило R1): код перемещается
  как есть, вместе с комментариями-обоснованиями (идемпотентность
  материализации, `hold`-маркер, суммирование частичных стирок). «Улучшать»
  логику по ходу запрещено. Единственное осознанное изменение — обёртка тел
  команд в `db.transaction_()` (шаг 6).
- **Инкрементально**: один шаг = один коммит; после каждого `npm test`
  зелёный.

## Состав модуля

Переезжают в `server/wash.js` (11 команд, сейчас `server/api/washes.js`):

- `startWash` (:174), `completeWash` (:196), `editWashData` (:249);
- `deferWash` (:294), `holdPartialWash` (:350), `addUnplannedWash` (:365);
- `cancelWash` (:559), `deleteWash` (:586);
- `confirmStorageCheck` (:625), `markIssued` (:656), `updateIssueDate` (:678);
- приватные хелперы, используемые только этими командами
  (`clientNameById_`, `notifyOwnerOnWorkerAction_` и т.п. — по факту
  использования).

Остаются в `server/api/washes.js` (read-эндпоинты, оркестраторы и чужие домены):

- `getDayList`, `getDeliveryPlan`, `getStorage`, `getDayReport`,
  `getSummaryReport`, `getFinanceSummary`, `getShiftCloseState`;
- `ensureWashesFromDelivery_` (:34) и `addToDelivery` (:540) — кросс-доменная
  оркестрация стирка↔развоз (поправка из R5);
- `closeShift` (:463) — это смена, отдельная концепция (модель смены —
  отдельный тикет);
- недельный план: `getWeekPlan`, `addWeekCard`, `moveWeekCard`,
  `removeWeekCard`, `weekMaterialized_`, `copyPrevWeek_`,
  `materializeTodayAllLaundries_` — оперируют визитами развоза;
- `notReadyForDelivery_` (:419) — read-хелпер, его забирает
  `deliveries.js` через фасад (циклический require разбирает R5: после R3
  хелпер переезжает в `wash.js`).

## Шаги (один шаг = один коммит)

### Шаг 1. Каркас

- Создать `server/wash.js` по паттерну `deliveries.js` (module-level require,
  экспорт функций, приватные хелперы с `_`).
- Перенести первую команду (например, `startWash`) вместе с приватными
  зависимостями — проверка паттерна адаптера в `washes.js`.
- `ensureWashesFromDelivery_` остаётся в `api/washes.js` (поправка из R5).

### Шаг 2. Ядро: complete / edit

- Перенести `completeWash`, `editWashData` + их приватные хелперы.
  Хендлеры в `washes.js` становятся тонкими адаптерами: делегируют в
  `wash.js` и возвращают результат как раньше.

### Шаг 3. Перенос и удержание: defer / hold / unplanned

- Перенести `deferWash`, `holdPartialWash`, `addUnplannedWash`.

### Шаг 4. Отмена и удаление: cancel / delete

- Перенести `cancelWash`, `deleteWash` (откат склада при отмене — как есть,
  со всеми комментариями).

### Шаг 5. Складская проверка и выдача: storageCheck / issued / issueDate

- Перенести `confirmStorageCheck`, `markIssued`, `updateIssueDate`.

### Шаг 6. Транзакции

- `db.transaction_()` в `server/db.js`: обёртка над `db.transaction(fn)`,
  экспортируется рядом с остальными хелперами db.
- Каждая команда `wash.js` оборачивается в транзакцию. Внимание: telegram-отправка
  (`notifyOwnerOnWorkerAction_`) — асинхронная и вне транзакции: сначала
  коммит, потом отправка, иначе откат транзакции оставит отправленное
  уведомление о несуществующем действии.
- `withLock_` в перенесённых командах удаляется; в остальном коде остаётся.

## Тесты

- **Фасад-тесты не правятся.** `server/test/api.characterization.test.js` и
  остальные (`server/test/*.test.js`) — эталон со времён R1; зелёные после
  каждого шага. Снапшот `Object.keys(api).sort()` не меняется.
- **Новый `server/test/wash.test.js`** (`node --test`, in-memory sqlite,
  те же хелперы `serverMocks.js`) бьёт прямо в интерфейс `wash.js` — то, что
  сегодня проверяемо только end-to-end:
  - `completeWash`: эффекты атомарны — WashItems + обновление стирки +
    clean-запись склада + смена + Log в одной транзакции;
  - `cancelWash`: откат склада (возврат dirty-записи) в той же транзакции;
  - `holdPartialWash` / `deferWash` по `partial`: маркер `hold`, перенос
    даты, восстановление dirty-записи;
  - транзакционность: сбой посередине команды (например, ошибка записи
    склада) не оставляет частично применённых изменений — смоделировать
    через подмену хелпера.

## Критерии приёмки

- Все 11 команд живут в `server/wash.js`; хендлеры `washes.js` — тонкие
  адаптеры; `washes.js` содержит read-эндпоинты, отчёты, оркестраторы
  (`ensureWashesFromDelivery_`, `addToDelivery`), `closeShift` и недельный
  план.
- Каждая команда выполняется в транзакции better-sqlite3; `withLock_` в
  границах модуля отсутствует.
- HTTP-контракт, имена методов, тексты ошибок и состав `api` не изменились;
  характеризационные тесты R1 зелёные без правок.
- `server/test/wash.test.js` покрывает оркестрацию эффектов и
  транзакционность; `npm test` зелёный.
- `deliveries.js`, `payroll.js`, `workhours.js`, `index.js`, клиент —
  не правились.

## Зависимости и отложено

- Зависит от R1 (выполнен). Желательно выполнить до новых фич, трогающих
  `washes.js` (очередные P6.x/P7.x) — иначе мерж-конфликты.
- Отложено (следующие тикеты, здесь не делать):
  - **R4. Выдача чистого — единый модуль**: `markIssued` / `deliver_clean` /
    `undo_deliver` сшиты по `issued_at === delivered_at`, у Storage нет
    `visit_id` («матч по метке времени»). После R3 `wash.js` становится
    естественным домом для этого шва;
  - **R5. Односторонний граф модулей**: циклический require
    `deliveries.js` ↔ фасад (`notReadyForDelivery_`, lazy require) и lazy
    require в `telegram.js`; фиксирует направление `deliveries → wash`
    (поправка про оркестраторы выше — оттуда);
  - **модель смены**: «Осталось со вчера» сейчас эвристика по складу
    (костыль, коммит b6e31e5); `closeShift` останется в `washes.js` до
    появления модуля «Смена»;
  - **reads-that-write**: read-эндпоинты материализуют стирки и копируют
    неделю; вынести материализацию из read-путей в явный шаг;
  - **дубль сборки счёта** между `getFinanceSummary` и `getClientInvoice`
    (R6);
  - **R2. TypeScript** (зарезервировано тикетом R1), SQL с
    `WHERE laundry_id = ?` вместо «хвост + JS-фильтр».
