# Тикет P6.1 — правка P6: откат склада при отмене забора грязного

**Ветка:** поверх реализации P6
**Оценка:** 0,5 дня
**Зависимость:** P6 (правка визита задним числом) уже реализован

## Контекст

P6 реализован по первой редакции тикета: `undo_pickup` при сданном на складе грязном (`dirty_handed_at` непуст) — жёсткий блок «правьте через склад». Это неправильно: кнопка «Передать грязное на склад» у водителя **массовая** (`driverHandover` сдаёт ВСЕ забранные точки разом), поэтому ошибочный забор почти всегда оказывается сданным — и самый частый случай правки оказывается заблокирован.

Цепочка данных: `pickup_dirty` (склад не трогает) → `driverHandover` создаёт клиенту пустую dirty-запись (`addStorageEntry_(client_id,'dirty',{})`, без веса) → приёмка создаёт из неё стирку (`consumeStorage_` проставляет `consumed_at` и `wash_id`).

## Что меняем

### 1. `undo_pickup`: блок → двухуровневый откат

Вместо отказа при `dirty_handed_at`:

1. Ищем dirty-запись этого клиента, созданную этой сдачей: `kind='dirty'`, `client_id` визита, `created_at === v.dirty_handed_at` (привязки visit_id у Storage нет — матч по метке времени, как `issued_at === delivered_at` в `undo_deliver`).
2. **Запись открыта** (`consumed_at` пусто — в стирку не ушла) → удалить её со склада (физически или маркером `consumed_at='cancelled'` — по соглашению проекта; в P6 для стирок/склада уже выбран какой-то вариант, держимся его), очистить `v.dirty_handed_at`, дальше обычный откат визита (`picked_at=''`, `pickup=''`, пересчёт status). На страницу «Склад» пользователь не идёт — правка делается из модала визита.
3. **Запись израсходована** (`wash_id` проставлен, стирка существует и не отменена) → ошибка с точной инструкцией: «Грязное уже принято в стирку (стирка №…). Отмените её на складе, затем повторите отмену забора». Состояние не меняем.
4. **Запись не нашлась** (уже правили вручную) → визит откатываем, в Log `warn: storage_not_found` в деталях `visit_correct`.

Нюанс массовой сдачи: `driverHandover` проставляет всем записям одну метку времени, и у клиента теоретически может оказаться несколько открытых dirty-записей с одинаковым `created_at` (визиты разных дней). Записи пустые и взаимозаменяемые (вес лежит на стирке, не на записи) — удаляем **одну** открытую из совпавших, в Log пишем, сколько найдено.

### 2. Проверить/дочинить `cancelWash`

Для пути «уже в стирке» (п. 3) нужна рабочая цепочка: владелец отменяет стирку → dirty-записи партии возвращаются на склад → `undo_pickup` проходит.

- Проверить, что `cancelWash` снимает расход с грязных записей (`wash_id` = id отменяемой стирки, `kind='dirty'`): `consumed_at=''`, `wash_id=''`. Это правильная семантика не только для правок: при отмене стирки физическое грязное бельё остаётся на складе и должно снова висеть в «К стирке».
- Если сейчас записи не возвращаются — добавить. Иначе после отмены стирки фантом зависнет на складе навсегда, а `undo_pickup` так и не разблокируется.

### 3. Деньги

Ничего нового: счёт (`getClientInvoice`), финансы и зарплата считаются вживую по полям визита; `isPaidVisit_` перестанет считать визит оплачиваемым после отката `picked_at`. Фантомная dirty-запись без `wash_id` на вес рейса-забора не влияла и после удаления не влияет.

## UI

Изменений почти нет (модал правки из P6 остаётся):
- Текст ошибки из п. 3 прилетает существующим тостом `useApiMutation` — просто смысловой текст с инструкцией (см. выше).
- Если в P6 кнопка «Отменить забор грязного» скрывалась/дизейблилась при `dirty_handed_at` — убрать это: теперь отмена доступна всегда, а блок срабатывает только при ушедшей в стирку партии.

## Тесты

**Сервер:**
- `undo_pickup`, грязное сдано, запись открыта → запись удалена со склада, `dirty_handed_at` очищен, визит `picked → planned` (или `both → delivered`), склад клиента больше не показывает фантом.
- Массовая сдача, у клиента 2 записи с одной меткой времени → удалена ровно одна открытая, вторая не тронута.
- Запись израсходована стиркой → ошибка с номером стирки, состояние визита и склада не изменилось.
- `cancelWash` возвращает dirty-записи партии на склад (`consumed_at=''`, `wash_id=''`); после него `undo_pickup` по этой точке проходит.
- Запись не найдена → визит откачен, `warn` в деталях события `visit_correct`.
- Регрессия P6: остальные операции (`undo_empty`, `undo_take_clean`, `undo_deliver`) не тронуты; права и тенант-изоляция как были.

**Вручную:**
- Водитель ошибочно «Забрал грязное» + «Передал на склад» → владелец/водитель отменяет забор из модала → фантом исчез со страницы «Склад» (счётчик «К стирке» −1).
- Тот же сценарий, но приёмка уже создала стирку → понятная ошибка → отмена стирки на складе → повторная отмена забора успешна.

## Критерии приёмки

1. Ошибочный забор отменяется в один клик из модала визита, пока партия не ушла в стирку, — без ручных действий на складе.
2. Партия в стирке → отказ с понятной инструкцией; цепочка «отменить стирку → отменить забор» работает до конца.
3. Отменённая стирка не оставляет висящих dirty-записей на складе.
4. Все откаты видны в журнале (кто, что, было/стало, сколько записей затронуто).
