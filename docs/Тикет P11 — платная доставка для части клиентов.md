# Тикет P11 — платная доставка для части клиентов

## Контекст

Клиенты делятся на два типа (подтверждено заказчиком):

- **Тип А — «платит всегда»:** любой состоявшийся рейс с доставкой платный, независимо от веса и числа ног. Порог «бесплатно от N кг» и тариф «в одну сторону» к такому клиенту **не применяются**.
- **Тип Б — текущая модель:** платит, только когда визит в одну сторону (oneway) или нога легче порога («Доставка менее N кг»); нога от порога — бесплатно.

Сейчас в `buildInvoice_` есть только тип Б: рейсы тарифицируются по ногам визита, позиции — «Доставка менее N кг» (пороговая, `max_kg`) и «Доставка в одну сторону/Забор» (`oneway=да`). Тип переключается **галочкой в карточке клиента**, не магией нулевых цен (пустая цена в ClientTariffs уже занята под «снять переопределение»; «0 = выключено» даёт молчаливый недобор денег и не виден в UI).

Взаимоисключаемость — по построению: режим выбирается один раз на клиента, двух доставочных строк по разным правилам в одном счёте быть не может.

## Часть 1 — схема и миграция

**Clients: новая колонка `paid_delivery`** ('да'/'', пусто = тип Б). Новые колонки подхватываются авто-ALTER'ом `createTables_`, миграция данных не нужна. Существующую колонку `type` НЕ переиспользуем — у неё своё назначение.

**BillingItems: новая колонка `per_visit`** ('да'/'') — маркер позиции «взимается за визит целиком, только у клиентов типа А». Тоже авто-ALTER.

**Новая фиксированная позиция прайса «Доставка»:** `unit='рейс'`, `kind='trip'`, `per_visit='да'`, остальное пусто, `sort` — сразу после пороговой позиции. Логистические позиции у нас закрыты для создания через UI, поэтому:

- `START_BILLING_ITEMS` — добавить объект для свежих установок.
- **Миграция v12** (SCHEMA_VERSION 11→12): вставить позицию в существующие БД. Идемпотентность: перед вставкой проверить «нет ли уже trip-позиции с per_visit='да'» — иначе свежая установка (сид + прогон миграций) создаст дубль.

Имя в счёте — статическое «Доставка» (динамическое имя сейчас только у пороговой, код `buildInvoice_` это уже различает, ничего менять не надо). `ext_code` пуст — владелец заполнит под 1С.

## Часть 2 — биллинг (`server/core.js`, `buildInvoice_`)

Два изменения, остальное не трогаем:

**1. Позиция «Доставка» исключается из общего пула ног — ВСЕГДА, для всех клиентов:**

```js
// per_visit-позиции в пул ног не входят: безъярусная trip-позиция иначе
// ловит ВСЕ рейсы ВСЕХ клиентов через pickByTier_ fallback (именно поэтому
// миграция v6 удаляла старую безъярусную «Доставку»).
const round = items.filter(function (b) { return b.kind === 'trip' && b.per_visit === 'да'; })[0];
const trips = items.filter(function (b) { return b.kind === 'trip' && b.per_visit !== 'да'; });
const paidDelivery = client.paid_delivery === 'да' && !!round;
```

**2. В цикле визитов — ветка по типу клиента** (логику ног и лифта не ломать):

```js
// legs как сейчас: picked_at → 'pickup', delivered_at → 'delivery'
if (paidDelivery) {
  // Тип А: один рейс = одна строка «Доставка», вес и число ног не важны.
  // Визит без ног (planned/empty) не тарифицируется — «всегда» = «когда рейс был».
  if (legs.length) add(round.id, 1);
} else {
  legs.forEach(function (leg) { /* текущая логика pickTripPosition_ без изменений */ });
}
// Подъём на этаж — общий для обоих типов, как сейчас
```

Цена позиции — обычным порядком через `resolvePrice_`: per-клиентское переопределение → дефолт прачки. У клиента типа А без цены на «Доставку» позиция попадает в `missing_prices` — **громкий** сигнал «включили платную доставку, забыли цену». Это осознанный выбор: для денег громкий отказ лучше молчаливого нуля.

Отменённые/empty-визиты не тарифицируются (фильтр уже есть), визит без ног строки не даёт — в обоих режимах.

## Часть 3 — UI

1. **Карточка клиента** (`(dashboard)/clients`, форма создания/редактирования): чекбокс «Платная доставка (каждый рейс)» — рядом с типом учёта (`accounting`). Сохранение — вместе с остальными полями клиента (`paid_delivery: 'да' / ''`).
2. **Прайс:** новая позиция появляется сама (миграция, `active='да'`). Проверить, что у неё доступны дефолтная цена и per-клиентские переопределения — механизм общий, но проглядеть, что закрытие создания trip-позиций не прячет её из списка.
3. Никаких переключателей в развозе/складе — тип клиента виден только в биллинге и карточке.

## Тесты

`server/test/`, к набору по `buildInvoice_`:

1. **Тип А, полный рейс ≥ порога.** `paid_delivery='да'`, визит с обеими ногами, каждая нога выше порога → ровно 1 × «Доставка»; «Доставка менее N кг» и oneway в счёте **отсутствуют** (взаимоисключаемость).
2. **Тип А, рейс в одну сторону.** Визит с одной ногой (например, `pickup_only`) → 1 × «Доставка», oneway нет. *(Дефолт семантики: один рейс = одна цена, нога не удешевляет. Если заказчик захочет «в одну сторону дешевле» — это отдельный тикет, см. «Что НЕ входит».)*
3. **Тип А без цены.** Галочка есть, цены на «Доставку» нет → позиция в `missing_prices`.
4. **Регрессия типа Б.** Клиент без галочки: полный рейс ≥ порога → доставки в счёте нет; ноги < порога → 2 × пороговая; одна нога → oneway. Как до тикета, построчно.
5. **Несостоявшиеся визиты.** planned (без ног) / cancelled / empty → ни одной доставочной строки в обоих режимах.
6. **Лифт** считается в обоих режимах одинаково.
7. **Миграция v12:** на БД без позиции — создаётся; повторный прогон и свежая установка (сид + миграции) — без дубля.

## Критерии приёмки

- [ ] В карточке клиента есть чекбокс «Платная доставка (каждый рейс)», сохраняется.
- [ ] Клиент типа А: любой состоявшийся визит → 1 × «Доставка» по его тарифу; порог и oneway к нему не применяются.
- [ ] Клиент типа Б: счёт построчно совпадает с поведением до тикета.
- [ ] В одном счёте не бывает одновременно «Доставка» и «Доставка менее N кг»/«в одну сторону».
- [ ] Тип А без цены → счёт подсвечивает позицию как без цены (missing_prices), а не молчит.
- [ ] Миграция v12 идемпотентна; на production-БД позиция появилась, дублей нет.
- [ ] Per-клиентская цена на «Доставку» перекрывает дефолт (разным клиентам типа А — разные цены).

## Что НЕ входит

- **«В одну сторону дешевле» для типа А** (отдельная цена за одноногий рейс). Если заказчик попросит — мини-тикет: второе ценовое поле у позиции или oneway-override.
- Скидки, абонементы, «N бесплатных рейсов в месяц».
- Зарплата водителя (PayRates) — к клиентскому биллингу отношения не имеет.
- Разбор старых счетов/периодов — правило действует с момента выкатки.

## Оценка

День: схема + миграция + биллинг с тестами — полдня, UI + прогон — полдня. Порядок коммитов: схема/миграция → биллинг + тесты → UI.
