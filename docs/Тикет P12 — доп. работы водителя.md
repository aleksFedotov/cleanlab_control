# Тикет P12 — доп. работы водителя (ввод водителем, правка владельцем, учёт в зарплате)

## Контекст

Водитель на точке иногда делает работу вне развоза (погрузка, подъём нестандарта, вынос и т.п.). Сейчас это никак не фиксируется: в зарплату можно добавить только ручную корректировку владельца (PayAdjustments — без клиента, без правки, вводит owner). Нужно:

1. Водитель **сам** вносит доп. работу со своего экрана.
2. Она учитывается в его зарплате.
3. Владелец может **редактировать** и удалять эти записи.
4. Запись хранит **client_id** — в будущем доп. работы будем выставлять клиенту в счёте (отдельный тикет; схема под это закладывается сейчас).

Принятые дефолты (если заказчик хочет иначе — скажи до старта):
- **Сумму вводит сам водитель** — он знает договорённость на месте. Владелец проверяет (Telegram-уведомление) и правит. Сумма — это **начисление водителю**; цена для клиента в будущем счёте будет отдельной величиной, их не смешиваем.
- Водитель может **удалить свою** запись (ошибся), но не редактировать — правка только у владельца.
- Сумма строго **> 0**: доп. работа — начисление; штрафы/удержания идут через корректировки владельца, как сейчас.
- Дата — не в будущем.

## Часть 1 — схема: таблица ExtraWorks

Новая таблица (SHEETS.EXTRA_WORKS = 'ExtraWorks'), создаётся авто-DDL, **миграция и bump SCHEMA_VERSION не нужны** (данные переносить неоткуда):

```js
// edited_by/edited_at — след правки владельца (деньги + будущий биллинг: история обязательна).
// client_id — клиент, у которого выполнена работа (задел под включение в счёт).
ExtraWorks: ['id', 'user_id', 'date', 'client_id', 'amount', 'comment',
  'created_by', 'created_at', 'edited_by', 'edited_at', 'laundry_id']
```

## Часть 2 — сервер: CRUD в payroll.js

Четыре метода, по образцу существующих payroll-функций (requireRole_, checkTarget_, findById_ + laundry_id, logEvent). Регистрация в API_ROLES по образцу payroll-методов.

**`addExtraWork(token, clientId, date, amount, comment)` — роли driver + owner:**
- валидации: `DATE_RE` и date ≤ сегодня; клиент найден в прачке и `active='да'`; `Number(amount) > 0`; непустой `comment` (trim) — что делал, обязательно;
- `user_id`: для driver — всегда `session.userId` (за себя); для owner — параметр `userId` (может внести за водителя: проверить через checkTarget_, что цель — водитель прачки);
- запись + logEvent `'extra_work_add'`;
- **Telegram владельцу при вводе водителем**: переиспользовать `notifyOwnerOnWorkerAction_` из wash.js (require цикла не создаёт), текст: `'💪 ' + actor + ': доп. работа — ' + клиент + ', ' + сумма + ' ₽ (' + комментарий + ')'`. Деньги, внесённые сотрудником, должны быть видны владельцу сразу.

**`editExtraWork(token, id, fields)` — только owner:**
- правит `date`/`client_id`/`amount`/`comment` (те же валидации), проставляет `edited_by`/`edited_at`;
- logEvent `'extra_work_edit'` со старыми и новыми значениями (как wash_edit);
- чужая прачка → «не найдена».

**`deleteExtraWork(token, id)` — driver (только свою) + owner (любую):**
- driver: `obj.user_id !== String(session.userId)` → «Нет доступа»;
- logEvent `'extra_work_del'` со снимком строки.

**`listExtraWorks(token, userId, from, to)` — driver (только свои) + owner (все/по сотруднику):**
- driver: фильтр принудительно `user_id = session.userId`, чужое не отдаём;
- owner: опциональные userId/from/to;
- в ответе подмешать `client_name` и `user_name` (как listPayAdjustments подмешивает name).

**Лёгкий список клиентов для водителя.** Для модалки нужен выбор клиента, а полный справочник водителю не светили. Завести `listClientsBrief(token)` (роли driver + owner) → `[{id, name}]` только активных, без контактов/адресов/ИНН. Если существующий метод списка клиентов уже отдаёт только лёгкие поля — можно расширить его роли вместо нового метода (на усмотрение исполнителя, но принцип «минимум полей» сохранить).

## Часть 3 — зарплата (computePayroll_)

Доп. работы — четвёртая составляющая наряду с точками/подъёмами/корректировками, но **отдельной строкой** (корректировки — это премии/штрафы владельца, смешивать нельзя):

- `loadPayrollInput_`: + `extraWorks` (фильтр по периоду, как adjustments).
- `computePayroll_`: собрать `extrasBy[user_id][date] = Σ amount`; в дневную сумму и в итог включать; в выход сотрудника добавить `extras_total` и (для детализации) дневной `extras`; `total = amountPoints + amountLifts + amountShift + adjustmentsTotal + extrasTotal`.
- Роль не важна: формально доп. работа может быть и у работника (владелец внесёт) — считаем одинаково для всех ролей.
- `getMyPayroll`: добавить `extras_total` (и дневные extras в days) — водитель видит в своём отчёте.

## Часть 4 — UI водителя (driver/page.tsx)

На вкладке «Маршрут» **новая секция «Доп. работы»** после «Адресов» (дата — та же `date` из DateNav, уже общая):

- Список записей за выбранную дату (из `listExtraWorks`): «клиент · сумма ₽ · комментарий», у своих — кнопка удаления с ConfirmDialog.
- Кнопка «＋ Доп. работа» → модалка: select клиента (из `listClientsBrief`), сумма (input number, min 0.01), комментарий (обязателен), дата = выбранная на экране. Сохранить → `addExtraWork`, тост «Доп. работа добавлена ✓», invalidate.
- Пустая дата → секция сворачивается в одну кнопку «＋ Доп. работа», пустым блоком не мозолим.

## Часть 5 — UI владельца

На странице зарплат (где корректировки и ставки) блок «Доп. работы»: таблица за период (дата, сотрудник, клиент, сумма, комментарий, кем создано/отредактировано), действия — **редактировать** (модалка с теми же полями) и удалить (ConfirmDialog). Плюс кнопка «＋» — внести за водителя (выбор сотрудника + те же поля).

В расчёте зарплаты у сотрудника показать строку «Доп. работы: N ₽» рядом с «Корректировки».

## Тесты

`server/test/`:

1. **addExtraWork (driver):** запись создана с его user_id; валидации: сумма ≤ 0 → ошибка; пустой комментарий → ошибка; неактивный/чужой клиент → ошибка; дата в будущем → ошибка; Telegram ушёл (mock), logEvent есть.
2. **Зарплата:** водителю extras вошли в total и extras_total; другому водителю и работнику — нет; корректировки не смешались с extras (отдельные поля).
3. **getMyPayroll:** extras_total присутствует и совпадает.
4. **editExtraWork (owner):** поля обновились, edited_by/edited_at проставлены, в логе старое→новое; чужая прачка → «не найдена».
5. **deleteExtraWork:** driver удаляет свою — ok, чужую — «Нет доступа»; owner удаляет любую; чужая прачка — «не найдена».
6. **listExtraWorks:** driver получает только свои записи; owner — фильтры по сотруднику/периоду.

## Критерии приёмки

- [ ] У водителя на экране маршрута есть «＋ Доп. работа»: клиент, сумма, комментарий; после сохранения запись видна за эту дату.
- [ ] Владельцу приходит Telegram о доп. работе, внесённой водителем.
- [ ] Запись учитывается в зарплате водителя отдельной строкой «Доп. работы» (не смешана с корректировками).
- [ ] Владелец может отредактировать и удалить любую запись; правки видны в Log с edited_by.
- [ ] Водитель не видит и не может трогать чужие записи.
- [ ] В записи хранится client_id — проверить SELECT'ом на production после выкатки.

## Что НЕ входит

- **Выставление доп. работ клиенту в счёте** — следующий тикет (схема уже готова: client_id + amount + date; вероятно, позиция прайса «Доп. работы» с отдельной клиентской ценой).
- Согласование/статусы («ожидает подтверждения владельца») — пока модель «доверие + Telegram + правка».
- Привязка к конкретному визиту (visit_id) — клиент достаточен; если биллинг потребует — добавим колонкой.

## Оценка

День: схема + сервер + зарплата с тестами — полдня, UI водителя и владельца — полдня. Порядок коммитов: схема → сервер + payroll + тесты → UI водителя → UI владельца.
