# R4. Углубление: единый переход «выдача чистого» (шов стирка ↔ развоз)

> Рефакторинг без изменения внешнего поведения. Переход «чистое выдано
> клиенту» сегодня реализован в трёх местах и сшит метками времени:
> `markIssued` (ручная выдача владельцем, `server/api/washes.js:656`),
> `driverAction`/`deliver_clean` (`server/deliveries.js:344-360`) и обратный
> `correctVisit`/`undo_deliver` (deliveries.js:444-467), который ищет стирки
> по `issued_at === v.delivered_at`. Откат забора (`undo_pickup`,
> deliveries.js:469-504) матчит грязную запись склада по
> `created_at === v.dirty_handed_at` — «Привязки visit_id у Storage нет —
> матч по метке времени». Добавляем `Storage.visit_id` (миграция v9) и
> концентрируем выдачу/возврат в командах модуля «Стирка» (`server/wash.js`
> из R3); хендлеры развоза становятся тонкими адаптерами. HTTP-контракт,
> имена методов, тексты ошибок и поведение не меняются.

## Принятые решения (контекст)

- **Шов принадлежит «Стирке».** Выдача и возврат чистого — переходы стирки
  (`stored/ready_clean → issued → stored`) с эффектами на склад; команды
  живут в `wash.js` (см. тикет R3). `deliveries.js` вызывает их из
  `driverAction` / `correctVisit` / `driverHandover`.
- **`Storage.visit_id` вместо меток времени.** Схема v9 (v8 уже занята
  колонкой `access_note`, см. `server/schema.js:4`): новая колонка
  `visit_id` у Storage, `SCHEMA_VERSION` 8 → 9. Метка времени больше не
  используется как ключ связи склад↔визит ни в одном пути.
- **Backfill исторических строк** в `migrateToV9_`: `visit_id` проставляется
  по тем же совпадениям, что используют нынешние откаты
  (`issued_at === delivered_at` для clean-записей выданных стирок,
  `created_at === dirty_handed_at` для dirty-записей сдачи). Семантика
  совпадения та же — хуже, чем сейчас, не станет; fallback-пути по меткам
  времени после миграции **удаляются**, двух путей матчинга в коде не
  остаётся. «Старые строки», которые не сматчатся, — это строки, созданные
  до появления меток `dirty_handed_at`/`delivered_at` (≈ до марта); они
  осознанно остаются с `visit_id = ''`.
- **`consumed_at` три-стейт сохраняем** (`''` — на складе, `'driver'` — у
  водителя, метка времени — выдано/израсходовано): замена на явную колонку
  состояния — отдельное решение, в этот заход не входит.
- **Транзакции: вся бизнес-операция = одна транзакция.** Команды
  `issueForVisit_`/`unissueForVisit_` сами визит **не пишут** — они мутируют
  `v` по существующему паттерну «мутирует v, пишет вызывающий». Вызывающие
  (`driverAction`, `correctVisit`, `driverReturnClean`) оборачиваются в
  `db.transaction_()` (из R3) **целиком**: склад + стирки + запись визита
  коммитятся или откатываются вместе. Сегодня атомарности нет вообще
  (`withLock_` — no-op заглушка), так что это не только устранение
  противоречия, но и реальное улучшение.
- **Перенос, не переписывание** (наследуем правило R1/R3): валидации,
  тексты ошибок, `warn`-ветки (`washes_not_found`, `storage_not_found`) и
  комментарии-обоснования сохраняются. Один шаг = один коммит; после
  каждого `npm test` зелёный.

## Шаги (один шаг = один коммит)

### Шаг 1. Схема v9: `Storage.visit_id` + backfill

- `server/schema.js`: колонка `visit_id` в `Storage` (после `wash_id`);
  `SCHEMA_VERSION` 8 → 9.
- `server/db.js`: `migrateToV9_()` — только backfill существующих строк.
  DDL не нужен: `createTables_` сам доносит новые колонки из HEADERS через
  `ALTER TABLE` (db.js:48-58). Backfill:
  - clean-записи с непустым `wash_id`, чья стирка `issued`: найти визит
    клиента с `delivered_at === wash.issued_at` → проставить `visit_id`;
  - dirty-записи: найти визит клиента с `dirty_handed_at === created_at` →
    проставить `visit_id`;
  - не сматчившееся (строки до появления меток, ручные правки истории)
    остаётся с `visit_id = ''`.
- Миграция идемпотентна через **маркер в Settings**: глобальный ключ
  `STORAGE_VISIT_ID_BACKFILL='done'` (laundry_id=''); страж — наличие
  маркера, после прогона он выставляется (`setTenantSetting_`, db.js:220).
  Страж по данным («есть строки с visit_id=''», как в `migrateToV7_`) не
  подходит: до-R2 строки навсегда остаются пустыми, и миграция
  пересканировала бы всю Storage при каждом старте. Подключается в оба
  списка (боевая и тестовая БД, db.js:27-44).

### Шаг 2. Запись `visit_id` в точках создания/взятия

- `driverHandover` (deliveries.js:537): dirty-запись склада создаётся с
  `visit_id` визита (сейчас связь только через `dirty_handed_at`).
- `takeCleanForVisit_` (deliveries.js:260): чистые записи, уходящие водителю,
  штампуются `visit_id` визита.
- `addStorageEntry_` (storage.js:11) принимает `opts.visit_id`.
- Поведение не меняется: чтение/откаты пока работают по-старому.

### Шаг 3. Команды выдачи в `wash.js`

- `issueForVisit_(v, laundryId)`: чистые записи визита
  (`visit_id + consumed_at='driver'`) → выданы; их стирки
  (`done|stored`) → `issued` + `issued_at`. Тело — перенос логики
  `deliver_clean` (deliveries.js:344-360) как есть. Визит не пишет —
  мутирует `v`, запись делает вызывающий (см. «Транзакции»).
- `unissueForVisit_(v, laundryId)`: откат выдачи — стирки выдачи
  (через складские записи визита, не по метке) → `stored`, их чистое →
  снова `'driver'`. Перенос `undo_deliver` (deliveries.js:444-467);
  `warn: 'washes_not_found'` сохраняется.
- `markIssued` (уже в `wash.js` после R3): ручная выдача без визита —
  `visit_id` остаётся пустым; поведение не меняется.
- `deliveries.js`: ветка `deliver_clean`/`both` в `driverAction` и
  `undo_deliver` в `correctVisit` делегируют в `wash.js`. Оба вызывающих
  (и `driverReturnClean` для симметрии) оборачиваются в
  `db.transaction_()` целиком — склад, стирки и запись визита атомарны.

### Шаг 4. Откаты на `visit_id`

- `undo_pickup` (deliveries.js:469-504): грязная запись ищется по
  `visit_id` визита вместо `created_at === dirty_handed_at`; ветки
  «запись израсходована → блок с инструкцией» и `warn: 'storage_not_found'`
  сохраняются.
- `returnCleanForVisit_` (deliveries.js:282) и
  `driverReturnClean`: чистое водителя по визиту — по `visit_id` вместо
  «все записи клиента со `'driver'`» (сейчас возврат задевает всё чистое
  клиента у водителя — при двух открытых визитах одного клиента это
  соседние точки; с `visit_id` возврат точечный).
- Fallback-матчинг по меткам времени удаляется из всех путей склад↔визит.

## Тесты

- **Существующие тесты не правятся**: `api.characterization.test.js`,
  `driver-return-clean.test.js`, `invoice.test.js` и остальные — зелёные
  после каждого шага. Биллинг (`pickupWeightKg_`/`deliveryWeightKg_`,
  core.js:241-266) читает `wash_id` партий — проверяется
  характеризационными тестами счёта, не трогаем.
- **Расширяем `server/test/wash.test.js`** (из R3; если R4 идёт без R3 —
  создать по тому же паттерну, `node --test`, in-memory sqlite):
  - `issueForVisit_` атомарна: склад + стирки + статус визита в одной
    транзакции; повторная выдача — ошибка «Чистое уже отдано»;
  - **откат при сбое**: исключение посередине операции (после записи
    склада, до записи визита) откатывает склад + стирки + визит целиком —
    тест честно проверяет заявленную транзакционную границу;
  - `unissueForVisit_` возвращает стирки в `stored`, чистое — `'driver'`;
    визит снова открыт;
  - `undo_pickup` удаляет именно свою dirty-запись по `visit_id` (два
    визита одного клиента в один день — удаляется запись своего визита);
  - `returnCleanForVisit_` точечен: при двух визитах клиента с чистым у
    водителя возвращается только бельё своего визита;
  - `migrateToV9_` на тестовой БД с историческими строками: backfill
    проставляет `visit_id` по меткам времени, несматчившееся — `''`;
    повторный запуск — no-op по маркеру `STORAGE_VISIT_ID_BACKFILL`
    (backfill не выполняется повторно).

## Критерии приёмки

- Ни один путь не ищет связь **склад↔визит** по меткам времени:
  `created_at === dirty_handed_at` удалено из кода, `issued_at ===
  delivered_at` для складских записей — тоже (оба сравнения остаются только
  в backfill `migrateToV9_`; см. также «Что НЕ входит» про связь
  стирка↔визит в `undo_deliver`).
- Выдача и возврат чистого — команды `wash.js`; `driverAction` /
  `correctVisit` / `driverHandover` — адаптеры над ними, обёрнутые в
  `db.transaction_()` целиком.
- HTTP-контракт, тексты ошибок, `warn`-ветки и поведение не изменились;
  весь существующий набор тестов зелёный без правок.
- `driverReturnClean` / `undo_take_clean` возвращают на склад только
  бельё своего визита.

## Что НЕ входит (известный остаточный риск)

- **Сцепка стирок в `undo_deliver` остаётся timestamp-based**: стирки
  выдачи ищутся по `issued_at === v.delivered_at` (deliveries.js:450-452).
  У Washes нет `visit_id`, и вносить его туда — отдельный тикет (модель
  связи стирка↔визит, не склад↔визит). Принимаем как известный остаточный
  риск: после R4 обе метки пишутся в одной транзакции (одна метка, один
  коммит), поэтому сцепка менее хрупкая, чем сегодня, но не устранённая.

## Оценка

1,5–2 дня: шаг 1 — 0,5 д, шаги 2–4 — 0,5–1 д, тесты и прогон — 0,5 д.

## Зависимости и отложено

- **Зависит от R3** (`server/wash.js`, `db.transaction_()`). Если R3 ещё
  не выполнен, R4 включает создание `wash.js` под свои команды — но
  предпочтительный порядок: R3 → R4.
- Желательно до новых фич развоза/правок задним числом (P6.x) — иначе
  мерж-конфликты в `deliveries.js`.
- Отложено (следующие тикеты, здесь не делать):
  - **модель смены**: эвристика «Осталось со вчера» (washes.js:76-91)
    cross-join'ит склад по клиенту и `created_at <= yesterday` — это
    механика смены, не выдачи; с `visit_id` она станет проще, но решается
    вместе с модулем «Смена»;
  - связь стирка↔визит (`Washes.visit_id`) — см. «Что НЕ входит»;
  - замена `consumed_at` три-стейт на явную колонку состояния склада;
  - reads-that-write (материализация из read-эндпоинтов);
  - циклический require `deliveries.js` ↔ фасад (`notReadyForDelivery_`) —
    после R4 стоит пересмотреть, не исчезла ли причина lazy require.
