# R10. Углубление: один владелец знания «что инвалидирует каждая мутация»

> Сегодня знание о том, какие чтения протухают после мутации, размазано по ~50
> местам вызова: `useApiMutation('startWash', { invalidate: 'operational' })`,
> строковые массивы `['payroll', 'payRates', 'myPayroll']`, ручные спреды
> `['refs', ...OPERATIONAL_PREFIXES]`. Отдельно: `method: string`
> (`client/src/hooks/use-api.ts:246`) — опечатка в имени метода живёт до рантайма;
> и ручной цикл инвалидации в обход хелпера (`plan/page.tsx:91`), который существует
> потому, что `removeWeekCard` там вызван вообще без `invalidate`.
>
> Веер из 10 префиксов (`OPERATIONAL_PREFIXES`, `client/src/lib/query-keys.ts:32`)
> при этом **не баг, а следствие реальных серверных связок** (стирка → склад →
> отчёт → финансы). Этот тикет не прореживает веер — он концентрирует знание
> в одном модуле: интерфейс мутации снова становится просто её именем.

## Принятые решения (контекст)

- **Только централизация и типизация.** Десятка префиксов остаётся как есть.
  Прореживание веера — отдельная история и только с замерами: недо-инвалидация
  даёт протухшие экраны, которые не ловятся тестами.
- **Карта исчерпывающая**: `Record` по всем мутациям — забытый метод ломает
  компиляцию, а не молча получает дефолт. Карта и есть тестовый шов клиента
  (unit-тестов у клиента нет; гарантия — TypeScript).
- **Union-тип имён выводится из ключей карты** (`keyof typeof`), отдельный
  руками поддерживаемый список не нужен: добавил запись в карту — имя появилось
  в типе. Источник истины о поведении — текущее *эффективное* поведение каждого
  вызова, перенос, не переписывание.
- **Осознанный дрейф чиним при выносе** (прецедент R7/R8) — три случая, см. шаг 1.
- Один шаг = один коммит; `npm run lint` + `npm run build` зелёные после каждого.

## Шаги (один шаг = один коммит)

1. **Модуль `client/src/lib/mutation-invalidation.ts`.** Карта
   `MUTATION_INVALIDATES` (мутация → массив префиксов из `qk` / `OPERATIONAL_PREFIXES`
   / пустой массив) и `export type MutationMethod = keyof typeof MUTATION_INVALIDATES`.
   Заполнение — по текущему поведению всех ~50 вызовов (контрольный список ниже),
   пустой массив там, где инвалидации сегодня нет и не нужно
   (`makeTelegramBindCode`, `resetUserPassword`, `rememberClientItemType`).
   Дрейфы, которые шаг чинит осознанно (зафиксировать в описании коммита):
   - `removeWeekCard` → `'operational'` везде: сегодня plan/page.tsx инвалидирует
     руками в `onSuccess` (plan/page.tsx:91), а week-card-dialog.tsx и
     week-copy-dialog.tsx — через опцию; поведение выравнивается;
   - `saveItemType` → `['refs', ...OPERATIONAL_PREFIXES]` везде: сегодня у трёх
     вызовов три варианта, включая «ничего» в `wash/[id]/AddItemTypeModal.tsx`;
   - `saveClientItemBilling` / `saveClient` / `deleteClient` и прочие refs-мутации
     со спредами `...OPERATIONAL_PREFIXES` — переносятся в карту как есть, спреды
     из компонентов исчезают.
2. **`useApiMutation` на карту.** Сигнатура: `method: MutationMethod`,
   опция `invalidate` удаляется; в `onSuccess` — lookup по карте
   (`OPERATIONAL` хранится как ссылка на `OPERATIONAL_PREFIXES`, ручной перебор
   остаётся только здесь). `useInvalidateOperational` схлопывается в этот lookup.
   Все ~50 вызовов мигрируют в этом же коммите — опция удалена, поэтому атомарно
   (коммит большой, но механический: удалить `invalidate: ...` из опций).
   Ручной цикл в `plan/page.tsx:91` удаляется. `Header.tsx:68`
   (`qc.invalidateQueries()` при смене прачки) — не мутация, не трогаем.

## Тесты и проверки

- `npm run lint` и `npm run build` в `client/` — зелёные. Сам тест — компилятор:
  вызов с именем вне карты не собирается; забытая в карте мутация не собирается.
- `npm run test:e2e` — зелёный (поведение инвалидации по построению не меняется,
  кроме трёх зафиксированных дрейфов).
- Ручная проверка одного сценария из каждого дрейфа: удаление карточки недели
  обновляет план; добавление типа номенклатуры из карточки стирки обновляет
  справочник.

## Критерии приёмки

- Ни одного `invalidate:` в опциях `useApiMutation` и ни одного ручного
  `invalidateQueries` вне `mutation-invalidation.ts` и `Header.tsx` (смена прачки).
- Опечатка в имени мутации — ошибка компиляции.
- Добавление новой мутации = одна строка в карте; без неё код не собирается.

## Оценка

0,5–1 день: карта (шаг 1) — основная работа, миграция вызовов механическая.

## Зависимости и отложено

- **Пересечение с R9**: кто ляжет вторым, тот добавляет `driverTakeClean` в карту
  (в R9) или мигрирует его вызов (в R10). Конфликт тривиальный.
- **Что НЕ входит:**
  - Прореживание `OPERATIONAL_PREFIXES` на группы — только с замерами числа
    запросов и отдельным решением; риск недо-инвалидации сегодня перевешивает
    экономию.
  - Типизация имён *query*-методов (`api<Res>('listExtraWorks', ...)` в хуках
    чтения) — тот же приём применим, но это удвоение карты без текущей боли.
  - `Header.tsx:68` (полная инвалидация при смене прачки) — осознанное поведение.
